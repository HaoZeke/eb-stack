#+TITLE: Dependency closure
#+OPTIONS: toc:t num:nil author:nil

A change to one easyconfig, one easyblock, or one bundled component is a
question about the other modules that name it. A planned software bill of
materials (SBOM) records that question: components, and the edges between
them, taken from the recipes before anything is installed. The commands on
this page answer it for the person writing an easyconfig, the person
reviewing one, the person changing an easyblock or a framework module, the
person triaging a Common Vulnerabilities and Exposures (CVE) entry, and
the person who keeps a software layer building.

Those questions show up for the European Environment for Scientific
Software Installations (EESSI). Other stacks raise them too. The fixture
trees in this repository supply the numbers, including the small
EESSI-shaped easystacks under ~tests/~. Each command takes an easyconfigs
tree and, where the question is a mounted prefix, a list of installed
modules. The runs write under ~/tmp/sbom-demo~. The version string is
~eb-stack 0.3.0~.

Those runs are the short form of the same commands. The how-tos list
every flag:
[[file:../howto/pr-overlap.org][pull-request overlap]],
[[file:../howto/rebuild-set.org][an in-place patch]],
[[file:../howto/component-reach.org][a named component]],
[[file:../howto/easyblock-reach.org][an easyblock change]], and
[[file:../howto/bump-recipe.org][a recipe bump]]. Output fields are in
[[file:../reference/formats.org][output formats]].

* A planned stack SBOM

~stack solve --sbom-out~ writes a CycloneDX 1.5 document for the selection.
~stack sbom --lock~ writes one later, from a lock that already exists. The
edges are not stored in the lock. Both commands read them from the
easyconfigs the lock names. A runtime dependency that is also selected is
a ~dependsOn~ edge. A builddependency is the component property
~eb_stack:buildDependsOn~. An unreadable path contributes no edge. The
document does not draw an edge from every package to every other package.

The fixture ~fixtures/gromacs_2025_to_next~ solves foss-2025b against a
foss-2025a baseline:

#+begin_src bash
eb-stack stack solve \
  --easyconfigs fixtures/gromacs_2025_to_next/easyconfigs \
  --policy fixtures/gromacs_2025_to_next/policies/prefer_newer.json \
  --baseline-easyconfigs fixtures/gromacs_2025_to_next/easyconfigs \
  --lock-out /tmp/sbom-demo/stack.lock.json \
  --sbom-out /tmp/sbom-demo/stack.cdx.json \
  --stack-diff-out /tmp/sbom-demo/stack.diff.md
#+end_src

#+begin_src text
lock=/tmp/sbom-demo/stack.lock.json packages=5
#+end_src

#+begin_src bash
eb-stack stack sbom \
  --lock /tmp/sbom-demo/stack.lock.json \
  --out /tmp/sbom-demo/stack-from-lock.cdx.json
#+end_src

#+begin_src text
sbom=/tmp/sbom-demo/stack-from-lock.cdx.json components=5 with_artifact_facts=0
#+end_src

~with_artifact_facts=0~ because those five recipes do not state a checksum.
The metadata property ~eb_stack:document_kind~ is
~planned-sbom-from-lock~ on both files. GROMACS is the only component with
outgoing runtime edges:

#+begin_src text
pkg:generic/GROMACS@2025.0?toolchain=foss-2025b
  pkg:generic/Python@3.12.3?toolchain=foss-2025b
  pkg:generic/OpenBLAS@0.3.27?toolchain=foss-2025b
  pkg:generic/OpenMPI@5.0.3?toolchain=foss-2025b
  pkg:generic/FFTW@3.3.10?toolchain=foss-2025b
#+end_src

The stack diff from the same solve classifies the move off the baseline.
Its summary is 2 unchanged, 0 added, 0 removed, 3 version-bumped. The
solve keeps the Fastest Fourier Transform in the West (FFTW) at 3.3.10,
and it keeps Python at 3.12.3. GROMACS moves 2024.1 to 2025.0, OpenBLAS
moves 0.3.23 to 0.3.27, and OpenMPI moves 4.1.5 to 5.0.3. That is the
closure of one generation step: four libraries under one application, and
three of the five packages changing version together.

* A checksum dict when the version changes

The hash in that SBOM has to name the artifact the new version will fetch.
A version bump with no new checksum clears the old digest to an empty
string and records a residual. It does not keep the previous tarball's
hash. A checksum dict is the case that used to drop entries: a key written
as a percent expression, an empty digest for a second file, and a key that
does not mention the version.

~local_arch~ is a name in the input recipe, not a value this command
computes. The empty robot directory satisfies ~--easyconfigs~. The
toolchain is ~system~ with an empty version, which is the system toolchain
this recipe already uses.

#+begin_src text
name = 'Pkg'
version = '1.0.0'
homepage = 'https://example.invalid/pkg'
description = 'Checksum dict with a percent-expression key'
toolchain = SYSTEM
source_urls = ['https://mirror.example.org/src']
sources = ['pkg-%(version)s.tar.gz']
checksums = [{
    'pkg-1.0.0-%s.tar.gz' % local_arch:
        'aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa',
    'pkg-1.0.0-linux-arm64.tar.gz': '',
    'notes.txt': 'cccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccc',
}]
moduleclass = 'tools'
#+end_src

#+begin_src bash
eb-stack package bump \
  --source /tmp/sbom-demo/ck/Pkg-1.0.0.eb \
  --toolchain-name system \
  --toolchain-version '' \
  --version 1.2.3 \
  --source-checksum dddddddddddddddddddddddddddddddddddddddddddddddddddddddddddddddd \
  --easyconfigs /tmp/sbom-demo/ck/robot \
  --out-dir /tmp/sbom-demo/ck/out
#+end_src

#+begin_src text
manifest=/tmp/sbom-demo/ck/out/package.plan.json
sbom=/tmp/sbom-demo/ck/out/package.sbom.cdx.json
lock=/tmp/sbom-demo/ck/out/locks/default.lock.json
easyconfig=/tmp/sbom-demo/ck/out/easyconfigs/p/Pkg/Pkg-1.2.3.eb
#+end_src

The emitted ~checksums~ entry is:

#+begin_src text
checksums = [{
    'pkg-1.2.3-%s.tar.gz' % local_arch:
        'dddddddddddddddddddddddddddddddddddddddddddddddddddddddddddddddd',
    'pkg-1.2.3-linux-arm64.tar.gz': '',
    'notes.txt': 'cccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccc',
}]
#+end_src

The expression key is renamed to 1.2.3 and receives the new digest. The
arm64 key is renamed and stays empty, so the old empty slot is not filled
with the amd64 hash. ~notes.txt~ is unchanged. The SBOM root hash is
SHA-256 ~dddddddddddddddddddddddddddddddddddddddddddddddddddddddddddddddd~,
the digest that was passed in. ~sources~ is still
~pkg-%(version)s.tar.gz~.

* Pull requests

A software-layer maintainer wants the shared modules. Two open pull
requests build those modules. An easyconfig reviewer wants the shared
files, the shared modules, and the added dependency. Two pull requests
touch those files and modules. One pull request adds the dependency the
other request needs. ~pr-overlap~ is that closure. ~prs/<N>.toml~ is the
build set for pull request N. ~overlap.toml~ and ~overlap.md~ are the
intersection.

The software-layer run uses ~tests/pr_overlap_fixtures~. The pull-request
file is the six records the integration test builds. Pull request 101 adds
Graphviz to the 2026.06 easystack, 102 adds gnuplot, 103 adds NewThing
pinned ~from-commit: abc~, 104 adds zlib on the rebuilds easystack, 105
adds Graphviz on the 2025.06 easystack, and 106 adds an absent easyconfig
pinned ~from-commit: def~. The default ~--eessi-version~ is 2026.06, so
105 is not a record.

forces a rebuild of some installed modules and not of others.
~rebuild-set~ closes the deployed easystacks and walks backward. The
fixture is ~tests/rebuild_set_fixtures~. ~changed.txt~ names
~zlib-1.3.1-GCCcore-15.2.0.eb~ and ~Absent-1.0.eb~.

* A component named by a CVE

The CVE names a component and a version. ~component-reach~ lists every
recipe in one toolchain generation that carries that component, then feeds
the recipes that contain the bytes into the same rebuild closure. On the
rebuild-set tree, zlib 1.3.1 in generation 2026.1:

#+begin_src bash
eb-stack component-reach \
  --component zlib \
  --version 1.3.1 \
  --generation 2026.1 \
  --easyconfigs tests/rebuild_set_fixtures/release \
  --installed tests/rebuild_set_fixtures/installed.txt \
  --easystack tests/rebuild_set_fixtures/eessi-2026.06-eb-5.4.0-2026.1.yml \
  --generated-at 2026-10-22T12:00:00Z \
  --out-dir /tmp/sbom-demo/component-zlib
#+end_src

#+begin_src text
component=zlib version=1.3.1 generation=2026.1 carriers=7 changed=2 must-rebuild=3 review=2 no-rebuild=5 out=/tmp/sbom-demo/component-zlib
#+end_src

The run reports seven carriers. The module itself is a carrier. Four
dependency or builddependency rows are carriers. The bundle extension is
a carrier. ~NotInstalled~ is a carrier, and it is not installed.
~changed=2~ counts zlib and the bundle. A recipe counts as a patched root
when it contains the component. A dependency on the component does not
count as a patched root. The closure then has three must-rebuild rows.
The bundle is both a root and an extension of zlib, which adds that extra
must-rebuild row. Review stays 2. No-rebuild is 5, one more than
~rebuild-set~. The bundle, taken as a root, also has PyApp as a runtime
dependent.

The component name matches as a whole token on those carriers. A
compat-layer line counts, and a longer name does not. Two recipes plus
~compat.txt~ containing ~curl 8.17.0~:

* An easyblock or a framework module

An easyblock change reaches the recipes that name that class, a subclass,
or the implied ~EB_<Name>~ class. ~--reverse~ then lists modules that
depend on a hit. The tree under ~/tmp/sbom-demo/ebreach/tree~ is four
recipes and three classes. ~CMakeMake~ subclasses ~ConfigureMake~.
~EB_GROMACS~ subclasses ~CMakeMake~. ~gromacs.eb~ has no ~easyblock~ line.
~zlib.eb~ sets ~easyblock = 'CMakeMake'~ and is the only installed module.
~make.eb~ sets ~ConfigureMake~. ~wrapper.eb~ depends on GROMACS. The
changed file is ~cmakemake.py~.
