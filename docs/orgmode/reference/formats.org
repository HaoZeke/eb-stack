#+TITLE: Output formats
#+OPTIONS: toc:t num:t author:nil

* Stack lock (~stack.lock.json~)

#+begin_src json
{
  "schema_version": 1,
  "toolchain": {"name": "foss", "version": "2025b"},
  "generation_label": "foss-2025b",
  "packages": [
    {
      "name": "GROMACS",
      "version": "2025.0",
      "toolchain": {"name": "foss", "version": "2025b"},
      "versionsuffix": null,
      "easyconfig_path": "foss-2025b/GROMACS-2025.0-foss-2025b.eb"
    }
  ],
    "solver": {
    "engine": "resolvo_cdcl_sat",
    "engine_version": "resolvo+eb_stack-0.3.0",
    "timestamp": "2026-01-01T00:00:00Z",
    "criteria": ["-notuptodate"]
  }
}
#+end_src

- ~schema_version~ :: ~1~.
- ~toolchain~ :: The policy's target toolchain (not necessarily every
  package's own toolchain field, though in practice they match).
- ~generation_label~ :: Optional human label, e.g. ~"foss-2025b"~ when
  produced from an easyconfig tree. Library callers may omit it for hand-built
  universes.
- ~packages~ :: One entry per co-selected package, sorted by name. Each
  entry is a ~LockPackage~: ~name~, ~version~, its own ~toolchain~, optional
  ~versionsuffix~, and the ~easyconfig_path~ it came from.
- ~solver~ :: ~engine~ is always ~"resolvo_cdcl_sat"~. ~engine_version~
  embeds the crate version. ~timestamp~ is RFC 3339, UTC, second precision.
  ~criteria~ is the CUDF list the solve applied, in order. A policy that
  sets neither ~criteria~ nor ~prefer_installed~ records ~["-notuptodate"]~.
  ~prefer_installed~ records ~["-changed", "-notuptodate"]~. An explicit
  ~criteria~ list is recorded as written. See the
  [[file:policy.org][policy reference]].

* Internal candidate universe

#+begin_src json
{
  "toolchain": {"name": "foss", "version": "2025b"},
  "generation_label": "foss-2025b",
  "candidates": [
    {
      "name": "GROMACS",
      "version": "2025.0",
      "toolchain": {"name": "foss", "version": "2025b"},
      "versionsuffix": null,
      "easyconfig_path": "foss-2025b/GROMACS-2025.0-foss-2025b.eb",
      "dependencies": [
        {"name": "OpenMPI", "version_req": "5.0.3"}
      ],
      "builddependencies": []
    }
  ]
}
#+end_src

~dependencies~ and ~builddependencies~ use the same ~DepReq~ shape and the
same ~version_req~ grammar as policy pins (see
[[file:policy.org][policy reference]]). This structure is a Rust/library input;
the version-one CLI builds it from repeatable ~--easyconfigs~ paths.

* Build list (~--build-list-out~)

Plain text, one easyconfig path per line, trailing newline, no blank lines:

#+begin_src text
fixtures/gromacs_2025_to_next/easyconfigs/foss-2025b/FFTW-3.3.10-foss-2025b.eb
fixtures/gromacs_2025_to_next/easyconfigs/foss-2025b/OpenBLAS-0.3.27-foss-2025b.eb
fixtures/gromacs_2025_to_next/easyconfigs/foss-2025b/OpenMPI-5.0.3-foss-2025b.eb
fixtures/gromacs_2025_to_next/easyconfigs/foss-2025b/Python-3.12.3-foss-2025b.eb
fixtures/gromacs_2025_to_next/easyconfigs/foss-2025b/GROMACS-2025.0-foss-2025b.eb
#+end_src

Order is a topological sort over the co-selected stack: a dependency's path
always appears before every co-selected package that needs it (runtime or
build-time). Ties are broken by package name for a deterministic order
independent of input list order or ~HashMap~ iteration. An empty lock
produces an empty file.

* Stack diff (~--stack-diff-out~)

Markdown, meant to be pasted directly into a pull request:

#+begin_src markdown
# Stack diff

Baseline (`baseline-from-eb-foss-2025a`) → solved (`foss-2025b`).

## Summary

- **unchanged**: 2
- **added**: 0
- **removed**: 0
- **version-bumped**: 3

## Packages

### FFTW — unchanged

- Baseline: `3.3.10` — `fixtures/gromacs_2025_to_next/easyconfigs/foss-2025a/FFTW-3.3.10-foss-2025a.eb`
- Solved: `3.3.10` — `fixtures/gromacs_2025_to_next/easyconfigs/foss-2025b/FFTW-3.3.10-foss-2025b.eb`

### GROMACS — version-bumped

- Baseline: `2024.1` — `fixtures/gromacs_2025_to_next/easyconfigs/foss-2025a/GROMACS-2024.1-foss-2025a.eb`
- Solved: `2025.0` — `fixtures/gromacs_2025_to_next/easyconfigs/foss-2025b/GROMACS-2025.0-foss-2025b.eb`
- Change: `2024.1` → `2025.0`

### OpenBLAS — version-bumped

- Baseline: `0.3.23` — `fixtures/gromacs_2025_to_next/easyconfigs/foss-2025a/OpenBLAS-0.3.23-foss-2025a.eb`
- Solved: `0.3.27` — `fixtures/gromacs_2025_to_next/easyconfigs/foss-2025b/OpenBLAS-0.3.27-foss-2025b.eb`
- Change: `0.3.23` → `0.3.27`

### OpenMPI — version-bumped

- Baseline: `4.1.5` — `fixtures/gromacs_2025_to_next/easyconfigs/foss-2025a/OpenMPI-4.1.5-foss-2025a.eb`
- Solved: `5.0.3` — `fixtures/gromacs_2025_to_next/easyconfigs/foss-2025b/OpenMPI-5.0.3-foss-2025b.eb`
- Change: `4.1.5` → `5.0.3`

### Python — unchanged

- Baseline: `3.12.3` — `fixtures/gromacs_2025_to_next/easyconfigs/foss-2025a/Python-3.12.3-foss-2025a.eb`
- Solved: `3.12.3` — `fixtures/gromacs_2025_to_next/easyconfigs/foss-2025b/Python-3.12.3-foss-2025b.eb`
#+end_src

Every package present in either the baseline or the solved lock is
classified once: ~unchanged~ (same version both sides), ~added~ (solved
only), ~removed~ (baseline only), or ~version-bumped~ (present both sides,
different version). Sections are sorted by package name.

* Planned SBOM (~--sbom-out~, CycloneDX 1.5)

Documents are built with the official [[https://crates.io/crates/cyclonedx-bom][cyclonedx-bom]]
crate (same models as cargo-cyclonedx), serialized as CycloneDX 1.5 JSON.

Opt-in: ~--sbom-out~ has no default filename. Omit it and ~stack solve~ writes
only the lock (and any requested build list / stack diff). ~eb-stack stack
sbom --lock LOCK~ defaults to ~stack.cdx.json~ because that command's sole
purpose is SBOM emission.

#+begin_src json
{
  "bomFormat": "CycloneDX",
  "specVersion": "1.5",
  "serialNumber": "urn:uuid:…",
  "version": 1,
  "metadata": {
    "timestamp": "2026-01-01T00:00:00Z",
    "tools": [{"vendor": "SURF", "name": "eb-stack", "version": "resolvo+eb_stack-0.3.0"}],
    "component": {
      "type": "application",
      "name": "easybuild-stack-foss-2025b",
      "version": "foss-2025b",
      "description": "Planned EasyBuild stack inventory from eb-stack lock (pre-install; not a post-build compliance scan)"
    },
    "lifecycles": [{"phase": "pre-build"}],
    "properties": [
      {"name": "eb_stack:document_kind", "value": "planned-sbom-from-lock"},
      {"name": "eb_stack:solver_engine", "value": "resolvo_cdcl_sat"},
      {"name": "eb_stack:toolchain", "value": "foss-2025b"}
    ]
  },
  "components": [
    {
      "type": "library",
      "bom-ref": "pkg:generic/GROMACS@2025.0?toolchain=foss-2025b",
      "name": "GROMACS",
      "version": "2025.0",
      "purl": "pkg:generic/GROMACS@2025.0?toolchain=foss-2025b",
      "properties": [
        {"name": "easybuild:toolchain", "value": "foss-2025b"},
        {"name": "easybuild:easyconfig_path", "value": "foss-2025b/GROMACS-2025.0-foss-2025b.eb"},
        {"name": "eb_stack:lifecycle", "value": "pre-install-plan"}
      ]
    }
  ],
  "dependencies": [
    {"ref": "pkg:generic/GROMACS@2025.0?toolchain=foss-2025b", "dependsOn": ["pkg:generic/Python@3.12.3?toolchain=foss-2025b", "pkg:generic/OpenBLAS@0.3.27?toolchain=foss-2025b", "pkg:generic/OpenMPI@5.0.3?toolchain=foss-2025b", "pkg:generic/FFTW@3.3.10?toolchain=foss-2025b"]}
  ]
}
#+end_src

Each component's ~bom-ref~ / ~purl~ is a synthetic ~pkg:generic/~ reference
(EasyBuild has no dedicated PURL type) embedding name, version, and
toolchain. Metadata ~lifecycles: pre-build~ and
~eb_stack:lifecycle: pre-install-plan~ mark a *planned* inventory from the
solver selection, not a scan of installed software.

~dependsOn~ edges:

- From ~stack solve --sbom-out~, ~eb-stack stack sbom --lock LOCK~, and
  the Model Context Protocol (MCP) tool ~eb_stack_sbom~: each package's declared runtime
  ~dependencies~, intersected with co-selected lock members, read from
  the easyconfigs the lock names. Checksums and source URLs come from
  those recipes too. Build-time deps (~builddependencies~) go on the
  component property ~eb_stack:buildDependsOn~ (comma-separated refs),
  not the runtime graph.
  A relative ~easyconfig_path~ is the recipe beside the lock file when
  that file exists, and otherwise the same path against the process
  directory. An unreadable path contributes no edges. The document does
  not invent all-to-all co-stack cycles. ~stack sbom~ and
  ~eb_stack_sbom~ report how many recipes were read. Empty ~dependsOn~
  arrays may be omitted by cyclonedx-bom serialization.

* Build order (~stack order --out~)

One easyconfig path per line, in dependency order. A generation that
builds one name twice lists both paths. ~--oldest~ changes which unpinned
version is chosen; it does not change the file shape.

Stdout names a repeated build as ~multiple builds of <name>: <ver-tc>, ...~
and ends with ~order=<path> builds=<N>~.

* Input hashes (~--hashes-out~)

One line per module, two spaces between the fields, the same layout as
~sha256sum~:

#+begin_src text
0123abcd...  GROMACS-2025.0-foss-2025b
#+end_src

The digest covers the easyconfig bytes and the hashes of everything that
module needs (~eb-stack-input-v1~). A recipe that cannot be read still
gets a line. Stdout reports ~incomplete=~ as how many of those lines are
not a complete closure.

* Easystack (~stack easystack~, ~--easystack-out~)

YAML with one ~easyconfigs~ list. A filename with no options is a string.
A filename with ~--option~ values is a mapping:

#+begin_src yaml
easyconfigs:
- OpenMPI-5.0.7-GCC-14.2.0.eb
- CUDA-12.8.0.eb:
    options:
      accept-eula-for: CUDA
#+end_src

~stack order --easystack-out~ writes the build sequence. ~stack easystack~
writes lock order, which is sorted by package name.

* Jenkins sections (~stack sections~)

The same build-list lines as the input, regrouped under ~#### Title ####~
headers taken from ~--from~. Commented-out lines stay commented out.
Packages the previous list does not name go under the ~--unfiled~ header.

* Source fetch (~sources.fetch.json~)

Written by ~package bump --fetch-checksums~ when at least one source was
considered. A JSON array:

#+begin_src json
[
  {
    "filename": "app-1.1.tar.gz",
    "url": "https://example.invalid/app-1.1.tar.gz",
    "sha256": "0123abcd",
    "errors": []
  }
]
#+end_src

~url~ and ~sha256~ are omitted when there is nothing to report. ~errors~
is omitted when the download succeeded. The downloaded bytes are not
stored in this file.

* Reproduction scores (~repro summary~)

~--scores~ is a directory of one ~<case>.json~ per case. ~--json~ prints
that array. Each object has ~case~, ~pull_request~ (a number or null),
~source~, ~target~, ~score~ (~EXACT~, ~SEMANTIC~, or ~MATERIAL~),
~allowance~ (lines forgiven), ~stale_allowance~, and ~residual_lines~.
A stale entry is ~{"kind": "absent_from_target", "line": "..."}~ or
~{"kind": "already_emitted", "line": "..."}~.

The table form is fixed:

#+begin_src text
| Case | PR | Score | Allowance | Residual |
|---+---+---+---+---|
#+end_src

~--ratchet~ reads ~note~, ~cases~ (case name to allowance count), and
~total~. ~total~ has to equal the sum of ~cases~.

* Pull-request build set (~eb-stack pr-overlap~)

One run writes three files. ~prs/<N>.toml~ is the SBOM for pull request ~N~:
the closure of the easystack entries it adds, minus modules already
installed. ~overlap.toml~ is the same build sets intersected. ~overlap.md~ is
that intersection as a report. Every file starts with the never-merge header.

~to_build~ is one sorted module per line, so the same line in two
~prs/<N>.toml~ files is a module both pull requests would build.
~sort | uniq -d~ on those lines, and a staging merge of the files, are the
overlap report.

** ~prs/<N>.toml~

| Field | Meaning |
|-
| ~schema_version~ | ~1~ |
| ~pr~ | Pull request number |
| ~head_sha~ | Head commit the record was computed for |
| ~title~ | Title at that commit, omitted when unknown |
| ~generated_at~ | RFC 3339 timestamp of the run |
| ~eessi_version~ | Stack version, from ~--eessi-version~ |
| ~installed_source~ | Label of the installed list |
| ~easystack_files~ | Easystack paths that contributed an entry |
| ~to_build~ | Module names that would be built, sorted, one per line |
| ~already_installed~ | Installed modules the walk reached and stopped at, sorted |
| ~unresolved~ | Requirements no easyconfig on the robot path satisfies, and ~easyblock <class> missing~ when ~--easyblocks~ was passed and no passed tree defines that class |
| ~notes~ | Present when the run recorded one: a class supplied by an ~include-easyblocks-from-commit~ tree, a commit an entry names whose tree was not passed, or an ~include-easyblocks-from-pr~. Omitted when empty |
| ~entries~ | The easystack lines the pull request adds |

A module whose easyblock class is missing is left out of ~to_build~. The
dependencies of that recipe stay. ~overlap.md~ prints each unresolved item
as ~- unresolved:~ and each note as ~- note:~.

Each ~[[entries]]~ table has ~easystack~, ~easyconfig~, and, when the entry
carries them, ~from_commit~ and ~eb_version~. A module name is
~name/version[-toolchain]versionsuffix~, with the system toolchain omitted.

~[[revisions]]~ is each easystack or easyconfig file the pull request
changes. ~kind~ is ~easystack~ or ~easyconfig~. ~base~ and ~head~ are the
file text when the fetch stored it. ~base_blob~ and ~head_blob~ are the git
blob ids of those bytes. A later merge-order reads this text, so the hunk
check does not need the original JSON. Omitted when the run stored none.

A worked record from an open 2026.06 pull request is in
[[file:../explanation/pr-overlap.org][from one easystack line to a build set]].

** ~overlap.toml~

| Field | Meaning |
|-
| ~schema_version~ | ~1~ |
| ~generated_at~ | Same timestamp as the records |
| ~eessi_version~ | Stack version |
| ~installed_source~ | Label of the installed list |
| ~prs~ | Pull request numbers that received a record, ascending |
| ~shared~ | Module to the pull requests that would build it, for modules more than one would build |
| ~pairs~ | Per pull request, the other pull requests it shares modules with, and which modules |

** ~overlap.md~

The same ~shared~ map as a table, then one section per pull request: how
many modules it builds, which other open pull requests it shares them with,
and any unresolved requirements. Pull requests are written as ~#N~ text when
~--repo-url~ is empty, and as links otherwise. The flag defaults to
~https://github.com/EESSI/software-layer~. The file links on GitHub without adding
an entry to a pull request timeline.

** ~merge-order.toml~

Written only with ~--merge-order~ (or ~--merged~, which turns that flag
on). The same never-merge header. Schema ~1~.

| Field | Meaning |
|-
| ~schema_version~ | ~1~ |
| ~generated_at~ | Same timestamp as the overlap index |
| ~installed_source~ | Label of the installed list |
| ~merged~ | ~--merged~ numbers, ascending. Empty when the flag is absent |
| ~steps~ | One step per pull request that is not in ~merged~ |
| ~cycles~ | Strongly connected sets. Each set is sorted, and the sets are sorted |
| ~conflicts~ | Easystack paths edited by two or more pull requests in a colliding way |

Each ~[[steps]]~ table:

| Field | Meaning |
|-
| ~position~ | 1-based index in ~steps~ |
| ~pr~ | Pull request number |
| ~after~ | Direct predecessors in the binding graph, ascending |
| ~builds~ | Residual ~to_build~ once every earlier step has merged, sorted |
| ~saves~ | Later pull requests, and the modules they no longer build |
| ~reason~ | Why this pull request was picked |

~saves~ is ~[[steps.saves]]~ with ~pr~ and ~modules~. A conflict has
~easystack~, ~prs~, and ~kind~. ~kind~ is ~same-insertion~ or ~same-entry~.

With ~--merge-order~, ~overlap.md~ gains a Merge order table: position,
pull request, build count, saves, and after. Conflicts follow that table
when any were found. Without the flag the Markdown file is unchanged.

** Easyconfigs records (schema 2)

~--kind easyconfigs~ writes schema 2. A software-layer record stays schema
1 and omits the fields below. ~eessi_version~ is omitted when it is empty.

| Field | Meaning |
|-
| ~schema_version~ | ~2~ |
| ~kind~ | ~easyconfigs~ |
| ~changed_easyconfigs~ | One entry per ~.eb~ path: ~path~, ~status~ (~added~, ~modified~, or ~deleted~), and ~module~ when the file parses |
| ~closure~ | Every module the changed easyconfigs reach, sorted, including the pull request's own modules |
| ~new_modules~ | Closure modules the base tree does not provide |
| ~reverse_dependents~ | Base-tree modules that resolve a dependency to a modified or deleted file of this pull request. Each entry has ~module~ and ~depth~. Depth 1 depends on the file itself |
| ~to_build~ | Closure minus ~--installed~ when that flag is set; otherwise the same modules as ~new_modules~ |

The other pull requests in the same run are on the robot path while
resolving, between the base tree and this pull request's own files.
~new_modules~ is still compared to the base tree alone.

~overlap.toml~ for this kind is schema 2 and adds ~rows~. There are 4
kinds:

| ~kind~ | When it is written |
|-
| ~same-file~ | 2 pull requests change one path. ~path~ is that path. ~prs~ lists the numbers |
| ~same-module~ | 2 pull requests add easyconfigs for one module. ~module~ is that module |
| ~shared-new-module~ | One module is in 2 pull requests' ~new_modules~ |
| ~depends-on~ | Pull request ~to~ reaches a module pull request ~from~ adds, and ~to~ does not also add it. ~modules~ lists those modules |

A software-layer index stays schema 1 and omits ~rows~.

* Rebuild set (~eb-stack rebuild-set~)

One run writes ~rebuild-set.json~, ~rebuild-set.md~, and one easystack per
EasyBuild version under ~rebuilds/~. The date in the easystack filename is
the ~YYYYMMDD~ taken from ~generated_at~. The version is the newest
EasyBuild version among the easystacks whose closure contains that
must-rebuild module, read from ~-eb-~ in the easystack filename. When no
filename carried a version, the file is ~unknown~.

** ~rebuild-set.json~

| Field | Meaning |
|-
| ~schema_version~ | ~4~ |
| ~generated_at~ | RFC 3339 timestamp of the run |
| ~installed_source~ | Label of the installed list |
| ~prefix~ | Installed prefix passed to ~--prefix~. Omitted when the flag was not passed |
| ~symbols_checked~ | ~true~ when ~--check-static~ ran |
| ~easystacks~ | Easystack paths that were read, sorted |
| ~changed~ | Patched easyconfig filenames, sorted |
| ~missing~ | Changed filenames that are not in the deployed graph |
| ~unresolved~ | Requirements no easyconfig satisfies, and easystack entries the robot path does not have |
| ~notes~ | A missing easyblock class, a ~from-commit~ whose tree was not given, or an install directory that was not found. Empty when there is nothing to say |
| ~counts~ | Row counts, with keys ~no-rebuild~, ~review~, and ~must-rebuild~ |
| ~rows~ | Installed reverse dependents. A review dependent is one row. The other classes stay one row per edge |

Each row has ~changed~, ~dependent~, ~dependent_easyconfig~, ~edge_kind~
(~changed~, ~runtime~, ~builddependency~, or ~extension~), ~class~
(~no-rebuild~, ~review~, or ~must-rebuild~), ~reason~, and ~eb_version~
when an easystack filename carried one. On a review row, ~changed~ is the
patched filenames joined by ~, ~. After ~--check-static~, a hit keeps only
the filenames whose exports were defined.

~rebuild-set.md~ is the same rows as a table, the counts line, the missing
filenames, and each note as ~- note:~.

** ~rebuilds/<YYYYMMDD>-eb-<version>-cve-patches.yml~

Class ~must-rebuild~ only. Entries are sorted by filename. ~rebuild: true~
is set because the module is already installed.

#+begin_src yaml
# In-place patches, same filename and version.
# Class must-rebuild only: the patched easyconfig, a bundle that ships it as an extension,
# and, when --check-static was used, a dependent that defines an export of the patched library.
# Generated by `eb-stack rebuild-set`.
easyconfigs:
  - Bundle-1.0-GCCcore-15.2.0.eb:
      options:
        rebuild: true
#+end_src

A worked classification is in
[[file:../explanation/rebuild-set.org][what an in-place patch forces a rebuild of]].

* Component reach (~eb-stack component-reach~)

One run writes ~component-reach.toml~, ~component-reach.json~, and
~component-reach.md~. The TOML file starts with
~# Generated by `eb-stack component-reach`.~

| Field | Meaning |
|-
| ~schema_version~ | ~1~ |
| ~generated_at~ | RFC 3339 timestamp of the run |
| ~component~ | Name that was asked for |
| ~version_req~ | Exact version, ~*~, or a requirement |
| ~generation~ | Toolchain generation |
| ~carriers~ | Easyconfigs and modules that carry it |
| ~changed~ | Filenames that contain it, fed to the closure |
| ~closure_counts~ | Row counts, keys ~no-rebuild~, ~review~, ~must-rebuild~ |
| ~closure_rows~ | Rebuild-set rows for ~changed~ |
| ~missing~ | Changed filenames absent from the closure graph |
| ~notes~ | A compat-layer hit, or a note the closure recorded |

Each carrier has ~role~ (~module~, ~dependency~, ~builddependency~,
~component~, ~extension~, ~crate~, ~source~, ~patch~, ~compat-layer~, or
~installed~), ~version~, ~easyconfig~ (empty for compat-layer and
installed-only rows), ~module~, and ~installed~ when a list was passed.

A closure row has the rebuild-set fields ~changed~, ~dependent~,
~dependent_easyconfig~, ~edge_kind~, ~class~, ~reason~, and ~eb_version~
when an easystack filename carried one. With no easystack the synthetic
stack is ~generation-<generation>.yml~ and ~eb_version~ is absent.

~component-reach.md~ is the carrier table, then the closure table, the
counts line, and each note as ~- note:~.
