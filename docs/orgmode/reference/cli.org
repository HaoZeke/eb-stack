#+TITLE: Command-line reference
#+OPTIONS: toc:t num:nil

~eb-stack~ has five namespaced command groups plus an MCP server. All paths
written by package commands are deterministic bundle artifacts.

* Command map

| Command | Purpose |
|-
| ~package inspect~ | Parse conda-forge, Spack, PyPI, CRAN, Cargo, LuaRocks, or Raku into a manifest and planned SBOM |
| ~package plan~ | Materialize profiles, solve with Resolvo, and emit recipes |
| ~package bump~ | Retarget an EasyBuild recipe and write the same canonical bundle |
| ~recipe check~ | Validate metadata and robot dependency availability |
| ~recipe lint~ / ~recipe format~ | Report upstream CI, test-suite, and review findings (E999, F541, W605, W291, E501, E2xx, ~EB_*~; ~eb --check-contrib~ merged when ~eb~ is installed) or mechanically wrap E501 lines |
| ~stack solve~ / ~stack sbom~ | Solve a multi-root stack or emit SBOM from a lock |
| ~target list~ / ~target doctor~ | Resolve layered target configuration and probe it |
| ~campaign run~ / ~campaign status~ | Execute or inspect a persisted build campaign |
| ~campaign finding ...~ | Claim and resolve typed build findings |
| ~mcp [--workspace]~ | Serve the same workflows over stdio, with recipe file tools rooted at ~--workspace~ |

* Package commands

** ~package inspect~

#+begin_src bash
eb-stack package inspect \
  --source PATH \
  --format auto|conda-forge|spack|pypi|cran|cargo|luarocks|raku \
  --toolchain-name foss \
  --toolchain-version 2026.1 \
  [--package-config PACKAGE.toml]... \
  --out-dir BUNDLE
#+end_src

This writes ~package.plan.json~ and ~package.sbom.cdx.json~. It does not solve
profiles or emit recipes, so it establishes no claim-ladder rung.

** ~package plan~

#+begin_src bash
eb-stack package plan \
  --source PATH \
  --format conda-forge|spack|pypi|cran|cargo|luarocks|raku \
  --toolchain-name foss \
  --toolchain-version 2026.1 \
  [--package-config PACKAGE.toml]... \
  [--source-checksum SHA256]... \
  --easyconfigs UPSTREAM \
  [--easyconfigs OVERLAY]... \
  --stack-policy STACK.toml \
  [--package-catalog CATALOG.toml]... \
  [--package-sources SOURCES.toml]... \
  [--easybuild-source DIR]... \
  [--conda-source DIR]... \
  [--spack-source DIR]... \
  [--cargo-source DIR]... \
  --out-dir BUNDLE
#+end_src

Package configs apply in argument order; later metadata, build policy, aliases,
and profile values override earlier layers. Later robot paths override earlier paths for the same EasyBuild identity.
~build.patches~ replaces the existing patch list by default. Set
~patches_mode = "merge"~ in the layer's ~[build]~ table to retain foreign or
preceding patches while adding or refining artifacts by filename.
Each requested product profile is solved independently and emits one lock plus
one conventional ~.eb~ file. The default profile has no suffix; non-default
profiles use their declared ~versionsuffix~.

Every emitted source needs a SHA-256 checksum. When a foreign recipe provides
only a VCS commit, repeat ~--source-checksum~ once for every source artifact in
manifest order. The values replace the positional source checksums in both the
manifest/SBOM and every emitted recipe. Planning fails before emission when
the count, shape, or completeness is invalid.

When a direct dependency has no compatible robot candidate, optional closure
inputs close the hole without inventing versions:

- ~--package-sources~ layers ordered EasyBuild / conda-forge / Spack / Cargo roots;
- ~--easybuild-source~, ~--conda-source~, ~--spack-source~, and ~--cargo-source~ push roots
  without a TOML file (order is discovery order);
- ~--package-catalog~ layers explicit foreign or ~easybuild-bump~ providers as
  ordered overrides.
- ~--emit-easyblock~ renders an easyblock skeleton for the package into
  ~easyblocks/<letter>/<module>.py~, ships it with the recipes, names the
  derived class as the easyblock and moves the variant options out of the
  emitted recipes. Without it a package that owes an easyblock gets a
  ~missing-easyblock~ residual. It does not combine with closure planning.
  ~package bump~ takes the same flag.

Robot candidates win over catalog entries. A closed plan writes companion
packages under ~packages/~, a shared ~easyconfigs/~ overlay, topological
~build-order.json~, and ~closure.sbom.cdx.json~. See
[[file:package-bundles.org][package bundles]] and the new-package how-to.

~--format cargo~ reads ~Cargo.toml~ or crates.io JSON. A PyPI leftover
whose run dependency is a PyO3 crate is closed by ~--cargo-source~, not
by a pip extra. Extra site packages that Warehouse omits belong in the
ingest: a JSON array of Warehouse objects, or later ~requirements.txt~
lines. Resolvo then takes the robot module when ~--easyconfigs~ provides
it. Do not hand-edit the emitted recipe for those names. A PEP 518
~build_system~ object with ~build-backend = mesonpy~ is the mesonpy hint:
listed ~requires~ become SAT build deps, and the emitter writes
~wrap_mode=default~ plus the shared cargo-on-EESSI isolation prelude
(host wrappers off, ~LINKER=${CC:-gcc}~, compat ~ld~ from ~uname -m~).
Hatchling stays a ~Python-bundle-PyPI~ module when the robot provides
it. See [[file:../howto/pypi-extend.org][site Python extras]].

** ~package bump~

#+begin_src bash
eb-stack package bump \
  --source RECIPE.eb \
  --toolchain-name foss \
  --toolchain-version 2024a \
  [--version VERSION] \
  [--source-checksum SHA256] \
  [--dep NAME=VERSION]... \
  --easyconfigs UPSTREAM \
  [--easyconfigs OVERLAY]... \
  [--hierarchy-fixture HIERARCHY.json] \
  [--stack-policy STACK.toml] \
  --out-dir BUNDLE
#+end_src

A bump writes the same manifest, planned SBOM, profile lock, and recipe layout
as a new package. ~--dep~ becomes a locked Resolvo override. Without
~--stack-policy~, the solver uses an unconstrained policy for the requested
toolchain. A changed package version without ~--source-checksum~ produces a
visible residual because source bytes cannot be inferred safely.

* Bundle layout

#+begin_src text
BUNDLE/
  package.plan.json
  package.sbom.cdx.json
  locks/<profile>.lock.json
  easyconfigs/<letter>/<name>/<recipe>.eb
#+end_src

~package plan~ and ~package bump~ establish the *resolves* claim only when all
requested locks and recipes are written successfully.

See [[file:package-bundles.org][package bundle reference]] for the complete
manifest, planned SBOM, profile-lock, residual, and recipe contract.

* Recipe commands

#+begin_src bash
eb-stack recipe check \
  --recipe RECIPE.eb \
  --easyconfigs UPSTREAM \
  [--easyconfigs OVERLAY]... \
  [--easyblocks DIR_OR_FILE]... \
  [--require-configopt FLAG]... \
  [--metadata-only]

eb-stack recipe lint RECIPE.eb [RECIPE.eb ...] [--base BEFORE.eb]
eb-stack recipe format RECIPE.eb [RECIPE.eb ...] [--dry-run]
eb-stack recipe format RECIPE.eb --out FORMATTED.eb
#+end_src

~recipe lint~ prints JSON with ~clean~, ~style~ (each finding carries
~path~, ~line~, ~column~, ~code~, ~severity~, and ~message~), ~check_contrib~,
and ~maintainer_acceptability~. It does not rely on ~eb --check-contrib~.
Style codes: E999 (not valid Python; the AST rules are skipped); the
easyconfigs CI lint F541 (f-string with no placeholder), W605 (invalid escape
sequence), and W291 (trailing whitespace, including inside ~description~);
the check-contrib pycodestyle codes E501 (longer than 120) and
E225/E226/E227/E228/E231; the easyconfigs test-suite checks
~EB_PY_NO_USER_SITE~, ~EB_SANITY_PATHS_SHAPE~, ~EB_LOCAL_VAR_NAMING~,
~EB_REDEFINED_PARAM~, and ~EB_CHECKSUM_COUNT~; and the review conventions
~EB_FMT_MISSING_F~, ~EB_FSTRING_QUOTE_REUSE~, ~EB_TEMPLATE_UNKNOWN~ (errors)
and ~EB_FMT_PERCENT~, ~EB_FMT_CONCAT~, ~EB_FMT_TEMPLATE_VAR~,
~EB_SHLIB_HARDCODED~, ~EB_DEP_DUPLICATE~ (warnings). With ~--base~, the file
before the edit, it also reports ~EB_FMT_TEMPLATE_REMOVED~ where a template
was replaced by a Python expression. ~f'lib/%(name)s.{SHLIB_EXT}'~ is correct
and not flagged. When ~eb~ is on ~PATH~, the command also runs
~eb --check-contrib~ and merges those findings (~origin~ is
~eb --check-contrib~). A missing ~eb~ is reported in ~check_contrib~ and does
not by itself fail the command. Error-severity findings do; warnings do not. ~recipe format~ only wraps mechanical E501 lines; the other codes stay in
~remaining~.

~recipe check~ refuses a recipe that is not valid Python. It prints the
structured dependency result and fails when package
metadata, checksum structure, required configuration flags, or robot
dependencies are invalid. Missing dependencies remain explicit work; the
command does not create placeholder recipes.

It also prints ~easyblock_resolution~: the class the recipe resolves to
(named, or derived from the software name), the file that defines it, its
bases and its ~extra_options~ keys. A bundle's own ~easyblocks/~ directory,
beside the ~easyconfigs/~ tree the recipe sits in, is searched first. Naming
~--easyblocks~ roots, such as an easyblocks checkout, asserts that the set is
complete: a software-specific ~EB_~ class found in none of them fails the
check with the message EasyBuild would stop on.

~recipe format~ only performs deterministic physical-line wrapping. Product
configuration, source selection, checksums, patches, and sanity paths remain
authored content.

* Stack commands

#+begin_src bash
eb-stack stack solve \
  --easyconfigs TREE [--easyconfigs OVERLAY]... \
  (--policy POLICY.json | --toolchain NAME/VERSION \
   [--root NAME]... [--roots-from-build-list LIST]...) \
  [--baseline-easyconfigs TREE] \
  [--baseline-toolchain-version VERSION] \
  [--baseline-easystack EASYSTACK.yml]... [--baseline-commits-from EB_REPO] \
  [--baseline-also-toolchain NAME/VERSION]... \
  [--filter-deps NAME,NAME...] \
  [--lock-out stack.lock.json] \
  [--sbom-out stack.cdx.json] \
  [--build-list-out build.list] [--build-list-excludes-baseline] \
  [--jenkins-build-list-out next.list [--jenkins-flags-from previous.list]... \
   [--jenkins-gpu-systems gpu-a,gpu-b]] \
  [--stack-diff-out stack.diff.md]

eb-stack stack sbom --lock stack.lock.json [--out stack.cdx.json]
#+end_src

~stack solve~ is the multi-root EasyBuild stack solver. Package-profile stack
preferences use the TOML schema documented with the package workflow; whole
stack solving uses the JSON ~Policy~ schema.

The baseline is either a previous generation (~--baseline-easyconfigs~, by
default the first ~--easyconfigs~ tree) or what a set of easystacks installs
(~--baseline-easystack~, repeatable). An easystack baseline is every entry
plus the closure its recipes pin, read from the ~--easyconfigs~ trees and kept
to the policy toolchain's hierarchy. An entry pinned with ~from-commit~ is read
from that commit of ~--baseline-commits-from~ when given, and matched by
filename otherwise. Entries that name no recipe are listed on standard error.
~--baseline-also-toolchain~ keeps another family's hierarchy in the baseline,
such as ~lfoss/2026.1~ beside a ~foss/2026.1~ solve. ~--filter-deps~ drops
every dependency on the named packages before the solve, as EasyBuild's
option of that name does; pass EESSI-extend's ~EASYBUILD_FILTER_DEPS~ list when
solving against an EESSI baseline, or the build list carries modules the
compat layer already provides.
Against an EESSI version's easystacks, ~unchanged~ in the stack diff means the
software layer already provides that module, and
~--build-list-excludes-baseline~ drops those modules (same name, version,
toolchain and versionsuffix) from the build list, leaving what the site layer
builds on top in dependency order.

A Jenkins build list is one easyconfig filename per line with optional ~eb~
flags, ~#~ for comments. ~--roots-from-build-list~ takes the package name of
every line as a root. ~--jenkins-build-list-out~ writes the solved build order
in that format; each package keeps the ~--hook~, ~--hooks~,
~--include-easyblocks~ and ~--accept-eula-for~ flags of its last line in the
~--jenkins-flags-from~ lists, while flags tied to the old recipe
(~--from-commit~, ~--from-pr~, ~--ignore-test-failure~, ~--rebuild~) stay
behind. A module whose name or versionsuffix says CUDA gets
~--include-systems~ with the ~--jenkins-gpu-systems~ list.

* Target commands

#+begin_src bash
eb-stack target list --config BASE.toml [--config SITE.toml]...
eb-stack target doctor \
  --config BASE.toml [--config SITE.toml]... \
  --target NAME
#+end_src

Target layers are applied in argument order. A complete target contains:

- transport: local or SSH;
- executor: direct or Slurm;
- runtime: host, Podman, or Docker;
- EasyBuild workload: command, robot paths, work root, temporary root, and
  environment.

~target doctor~ probes each layer separately and reports the exact routed
command, exit code, stdout, and stderr.

See [[file:targets.org][build target configuration]] for complete layer schemas,
replacement semantics, ABI isolation, and the runnable local Podman target.

* Campaign commands

#+begin_src bash
eb-stack campaign run \
  --bundle BUNDLE \
  --config BASE.toml [--config SITE.toml]... \
  --target NAME \
  --state CAMPAIGN.json

eb-stack campaign status --state CAMPAIGN.json

eb-stack campaign finding claim \
  --state CAMPAIGN.json --id FINDING --owner WORKER

eb-stack campaign finding resolve \
  --state CAMPAIGN.json --id FINDING --owner WORKER \
  --action TEXT --evidence TEXT [--change PATH]...
#+end_src

~campaign run~ resumes state with matching package identity, increments the
attempt, stages the bundle, runs every emitted recipe, and executes each
profile's verification commands. Transport, executor, runtime, interrupted,
checksum, patch, dependency, configure, compile, link, test, install, sanity,
resource, timeout, and unknown failures are persisted as typed findings.

Finding claims are exclusive. A resolution records an action, evidence, and
changed paths. A successful retry supersedes matching open or in-progress
findings. Campaign state reports ~resolves~, ~builds~, and ~binary_verified~
independently.

See [[file:campaigns.org][campaign state and typed findings]] for the serialized
state, claim ladder, class/disposition table, and repair protocol.

* MCP

#+begin_src bash
eb-stack mcp [--workspace ROOT]
#+end_src

~--workspace~ sets ~EB_STACK_WORKSPACE~ for the recipe file tools. When it is
omitted, an existing ~EB_STACK_WORKSPACE~ is kept, and otherwise the server's
current directory is the root.

The stdio server exposes one tool per CLI workflow, plus four sandboxed file
tools:

- ~eb_package_inspect~, ~eb_package_plan~, ~eb_package_bump~;
- ~eb_recipe_read~, ~eb_recipe_list~, ~eb_recipe_edit~, ~eb_recipe_write~,
  ~eb_recipe_grep~;
- ~eb_recipe_check~, ~eb_recipe_lint~, ~eb_recipe_format~;
- ~eb_stack_solve~, ~eb_stack_sbom~;
- ~eb_target_list~, ~eb_target_doctor~;
- ~eb_campaign_run~, ~eb_campaign_status~;
- ~eb_campaign_finding_claim~, ~eb_campaign_finding_resolve~.

~eb_recipe_read~, ~eb_recipe_list~, ~eb_recipe_edit~, ~eb_recipe_write~, and
~eb_recipe_grep~ resolve every path inside that root. A ~..~ component, an absolute path
outside the root, or a symlink whose target leaves the root is rejected and
the file is not opened. ~eb_recipe_edit~ replaces an exact string. If ~old~
matches more than once, the file is left unchanged unless ~replace_all~ is
true. ~eb_recipe_write~ does not create parent directories. ~eb_recipe_grep~
searches for a literal ~pattern~ (a regular expression when ~regex~ is true)
under ~path~ (default the root), skips ~.git~, does not follow symlinks, and
returns at most ~max_matches~ (default and limit 200) matches.
~eb_recipe_check~ requires ~easyconfigs~ (~minItems~ 1). An empty list
returns ~argument easyconfigs requires at least one path~. A ~.eb~ file there
stands for the ~easyconfigs~ directory it sits in; any other file is an error
that asks for a robot directory. A recipe that is not valid Python is refused.
~eb_recipe_lint~ takes a ~recipes~ path array and returns ~results~ plus
~check_contrib~, using the same findings as ~recipe lint~.

MCP results include the same artifacts, claims, findings, and next actions as
the CLI. There is no separate compatibility command surface.

~eb_package_plan~ accepts the CLI's repeated source-checksum input as a
~source_checksums~ string array, and the catalog / source-root inputs as
~package_catalogs~, ~package_sources~, ~easybuild_sources~, ~conda_sources~,
and ~spack_sources~ arrays. ~eb_package_bump~ optionals include ~version~,
~source_checksum~, ~dependencies~ (object map), ~hierarchy_fixture~, and
~stack_policy~. ~eb_recipe_lint~ takes a ~recipes~ path array and returns
reviewer-style findings plus ~check_contrib~. ~eb_recipe_check~'s
~easyconfigs~ array has ~minItems~ 1. ~eb_recipe_read~, ~eb_recipe_list~,
~eb_recipe_edit~, and ~eb_recipe_write~ edit files only inside the workspace
root.
