#+TITLE: Command-line reference
#+OPTIONS: toc:t num:nil author:nil

~eb-stack~ has six namespaced command groups (~package~, ~recipe~,
~stack~, ~target~, ~campaign~, ~repro~), four reports (~easyblock-reach~,
~pr-overlap~, ~rebuild-set~, ~component-reach~), and a Model Context Protocol (MCP) server.
~--version~ prints the crate version. All paths written by package commands
are deterministic bundle artifacts.

* Exit status

| Code | When |
|-
| 0 | The command finished the work it was asked to do |
| 1 | The work was attempted and failed: a missing or unreadable file, a document that does not parse, a check that found errors, a network fetch that failed, a doctor probe, or a campaign whose build failed |
| 2 | The command line was rejected before that work: a missing or unknown flag (clap), or a flag value or combination the command does not accept |

A rejected value names the flag and the value. A missing file names the flag and the path. Status 2 is the same status clap already uses. A recipe that fails ~recipe lint~ or ~recipe check~ is status 1: the files were read and the check failed.

~--help~ for every command has an example and a description of every flag. A default that the command applies is printed in that help. A directory that receives several artifacts is ~--out-dir~. A single output file is ~--out~ (~--lock-out~ for the lock ~stack solve~ writes). ~--installed~, ~--easyconfigs~, ~--filter-deps~, and ~--generated-at~ use those names on every command that takes them.

Package commands take the toolchain as ~--toolchain-name~ and ~--toolchain-version~, or as ~--toolchain name/version~, which is the spelling ~stack solve~ uses. The two forms are not combined. ~--toolchain-name~ defaults to ~foss~ on ~package inspect~ and ~package plan~.

* Command map

| Command | Purpose |
|-
| ~package inspect~ | Parse conda-forge, Spack, PyPI, Comprehensive R Archive Network (CRAN), Cargo, LuaRocks, or Raku into a manifest and planned software bill of materials (SBOM) |
| ~package plan~ | Materialize profiles, solve with Resolvo, and emit recipes |
| ~package bump~ | Retarget an EasyBuild recipe and write the same canonical bundle |
| ~recipe easyblock~ | Print the easyblock class name EasyBuild derives for a software name |
| ~recipe templates~ | Emit template constants and derived-key rules, or the values `--name` and `--version` resolve |
| ~recipe hierarchy~ | Emit known toolchain hierarchies as JSON |
| ~recipe check~ | Validate metadata and robot dependency availability |
| ~recipe lint~ / ~recipe format~ | Report upstream CI, test-suite, and review findings (E999, F541, W605, W291, E501, E2xx, ~EB_*~; ~eb --check-contrib~ merged when ~eb~ is installed) or mechanically wrap E501 lines |
| ~stack solve~ / ~stack sbom~ | Solve a multi-root stack or emit SBOM from a lock |
| ~stack order~ | Sequence every pinned build a set of roots needs |
| ~stack easystack~ | Write a lock as the YAML ~eb --easystack~ reads |
| ~stack sections~ | Regroup a Jenkins build list under a previous list's headers |
| ~repro summary~ | Print a reproduction scoreboard from collected case scores |
| ~pr-overlap~ | Close open pull-request easystack additions against an installed stack and report shared builds |
| ~rebuild-set~ | Classify the installed reverse dependents of easyconfigs patched in place |
| ~component-reach~ | List who carries a component in one generation and close their rebuild set |
| ~target list~ / ~target doctor~ | Resolve layered target configuration and probe it |
| ~campaign run~ / ~campaign status~ | Execute or inspect a persisted build campaign |
| ~campaign finding ...~ | Claim and resolve typed build findings |
| ~mcp [--workspace]~ | Serve each CLI workflow over stdio, including ~pr-overlap~, ~rebuild-set~, ~component-reach~, and ~easyblock-reach~, with recipe file tools rooted at ~--workspace~ |
| ~easyblock-reach~ | Report easyconfigs and installed modules reached by an easyblock or framework change |

* Package commands

The toolchain is ~--toolchain~ name/version, or the split flags ~--toolchain-name~ and ~--toolchain-version~. The two forms are not combined.

** ~package inspect~

#+begin_src bash
eb-stack package inspect \
  --source PATH \
  --format auto|conda-forge|spack|pypi|cran|cargo|luarocks|raku \
  --toolchain-name foss \
  --toolchain-version 2026.1 \
  [--package-config PACKAGE.toml]... \
  --out-dir BUNDLE
#+end_src

This writes ~package.plan.json~ and ~package.sbom.cdx.json~. It does not solve
profiles or emit recipes, so it establishes no claim-ladder rung.

** ~package plan~

#+begin_src bash
eb-stack package plan \
  --source PATH \
  --format auto|conda-forge|spack|pypi|cran|cargo|luarocks|raku \
  --toolchain-name foss \
  --toolchain-version 2026.1 \
  [--package-config PACKAGE.toml]... \
  [--source-checksum SHA256]... \
  [--package-index FILE] \
  --easyconfigs UPSTREAM \
  [--easyconfigs OVERLAY]... \
  --stack-policy STACK.toml \
  [--package-catalog CATALOG.toml]... \
  [--package-sources SOURCES.toml]... \
  [--easybuild-source DIR]... \
  [--conda-source DIR]... \
  [--spack-source DIR]... \
  [--cargo-source DIR]... \
  --out-dir BUNDLE
#+end_src

Package configs apply in argument order; later metadata, build policy, aliases,
and profile values override earlier layers. Later robot paths override earlier paths for the same EasyBuild identity.
~build.patches~ replaces the existing patch list by default. Set
~patches_mode = "merge"~ in the layer's ~[build]~ table to retain foreign or
preceding patches while adding or refining artifacts by filename.
Each requested product profile is solved independently and emits one lock plus
one conventional ~.eb~ file. The default profile has no suffix; non-default
profiles use their declared ~versionsuffix~.

Every emitted source needs a SHA-256 checksum. When a foreign recipe provides
only a VCS commit, repeat ~--source-checksum~ once for every source artifact in
manifest order. The values replace the positional source checksums in both the
manifest/SBOM and every emitted recipe. Planning fails before emission when
the count, shape, or completeness is invalid.

~--package-index FILE~ supplies a version for a dependency that states none.
The file is either a CRAN ~PACKAGES~ index or a ~name==version~ list, one pin
per line. A range is not a version and supplies nothing.

Passing ~--easyconfigs~ always uses the closure writer, because that tree is
also a discovery root. The bundle then contains ~closure.plan.json~,
~closure.sbom.cdx.json~, and ~build-order.json~ even when no companion was
needed. ~--emit-easyblock~ does not combine with that writer.

When a direct dependency has no compatible robot candidate, further closure
inputs close the hole without inventing versions:

- ~--package-sources~ layers ordered EasyBuild / conda-forge / Spack / Cargo roots;
- ~--easybuild-source~, ~--conda-source~, ~--spack-source~, and ~--cargo-source~ push roots
  without a TOML file (order is discovery order);
- ~--package-catalog~ layers explicit foreign or ~easybuild-bump~ providers as
  ordered overrides.
- ~--emit-easyblock~ renders an easyblock skeleton for the package into
  ~easyblocks/<letter>/<module>.py~, ships it with the recipes, names the
  derived class as the easyblock and moves the variant options out of the
  emitted recipes. Without it a package that owes an easyblock gets a
  ~missing-easyblock~ residual. It does not combine with closure planning.
  ~package bump~ takes the same flag.

Robot candidates win over catalog entries. A closed plan writes companion
packages under ~packages/~, a shared ~easyconfigs/~ overlay, topological
~build-order.json~, and ~closure.sbom.cdx.json~. See
[[file:package-bundles.org][package bundles]] and the new-package how-to.

~--format cargo~ reads ~Cargo.toml~ or crates.io JSON. A ~Cargo.toml~ names
no crate tarball, so plan stops with ~foreign package plan has no source
artifacts~. The crates.io JSON carries the checksum, and that is what plan
emits from. A PyPI leftover
whose run dependency is a PyO3 crate is closed by ~--cargo-source~, not
by a pip extra. Extra site packages that Warehouse omits belong in the
ingest: a JSON array of Warehouse objects, or later ~requirements.txt~
lines. Resolvo then takes the robot module when ~--easyconfigs~ provides
it. Do not hand-edit the emitted recipe for those names. A PEP 518
~build_system~ object with ~build-backend = mesonpy~ is the mesonpy hint:
listed ~requires~ become SAT build deps, and the emitter writes
~wrap_mode=default~ plus the shared cargo-on-EESSI isolation prelude
(host wrappers off, ~LINKER=${CC:-gcc}~, compat ~ld~ from ~uname -m~).
Hatchling stays a ~Python-bundle-PyPI~ module when the robot provides
it. See [[file:../howto/pypi-extend.org][site Python extras]].

** ~package bump~

#+begin_src bash
eb-stack package bump \
  --source RECIPE.eb \
  --toolchain-name foss \
  --toolchain-version 2024a \
  [--version VERSION] \
  [--source-checksum SHA256] \
  [--dep NAME=VERSION]... \
  --easyconfigs UPSTREAM \
  [--easyconfigs OVERLAY]... \
  [--hierarchy-fixture HIERARCHY.json] \
  [--stack-policy STACK.toml] \
  [--package-config PACKAGE.toml]... \
  [--strict-patches] \
  [--emit-easyblock] \
  [--fetch-checksums] \
  --out-dir BUNDLE
#+end_src

A bump writes the same manifest, planned SBOM, profile lock, and recipe layout
as a new package. ~--dep~ becomes a locked Resolvo override. The solve fails
when that name is not in the robot tree. A name the recipe does not depend on
stays out of the emitted dependency list, and the lock records the pin outcome.
Without ~--stack-policy~, the solver uses an unconstrained policy for the
requested toolchain. A changed package version without ~--source-checksum~
clears the old digest and produces a visible residual, because source bytes
cannot be inferred safely. ~--package-config~ is repeatable and applies after
the source recipe is parsed, as it does for ~package plan~. ~--strict-patches~
fails the bump when a patch's fate across a version change cannot be decided
from the tree; without it the patch is carried and a ~patch-decision~ residual
records the review flag. ~--emit-easyblock~ is the same flag as on ~package plan~.
~--fetch-checksums~ downloads each ~sources~ entry from the recipe's
~source_urls~ when the version changed and ~--source-checksum~ was omitted,
and writes that SHA-256 into the recipe and the SBOM. A git checkout, a
missing URL, or a failed download stays empty. The attempts are
~sources.fetch.json~ (one object per source: ~filename~, ~url~, ~sha256~,
~errors~) and a ~source:fetch~ residual. See
[[file:formats.org][output formats]].

* Bundle layout

#+begin_src text
BUNDLE/
  package.plan.json
  package.sbom.cdx.json
  closure.plan.json
  closure.sbom.cdx.json
  build-order.json
  locks/<profile>.lock.json
  easyconfigs/<letter>/<name>/<recipe>.eb
#+end_src

~package plan~ writes the three closure files whenever ~--easyconfigs~ is
passed. ~package inspect~ writes only the plan and planned SBOM.

~package plan~ and ~package bump~ establish the *resolves* claim only when all
requested locks and recipes are written successfully.

See [[file:package-bundles.org][package bundle reference]] for the complete
manifest, planned SBOM, profile-lock, residual, and recipe contract.

* Recipe commands

#+begin_src bash
eb-stack recipe easyblock NAME
eb-stack recipe easyblock -- -NAME
eb-stack recipe easyblock --charmap

eb-stack recipe templates --export
eb-stack recipe templates --name NAME --version VERSION

eb-stack recipe hierarchy [--export]

eb-stack recipe check \
  --recipe RECIPE.eb \
  --easyconfigs UPSTREAM \
  [--easyconfigs OVERLAY]... \
  [--easyblocks DIR_OR_FILE]... \
  [--require-configopt FLAG]... \
  [--metadata-only] \
  [--verify-sources \
     [--seeded-from ECOSYSTEM \
        [--seeded-source-url URL] \
        [--seeded-git GIT_REMOTE]] \
     [--source-tree DIR]] \
  [--strict]

eb-stack recipe lint RECIPE.eb [RECIPE.eb ...] [--base BEFORE.eb]
eb-stack recipe format RECIPE.eb [RECIPE.eb ...] [--dry-run]
eb-stack recipe format RECIPE.eb --out FORMATTED.eb
#+end_src

~recipe easyblock~ prints the class EasyBuild derives from a software name
(~EB_~ plus the framework character map). ~--charmap~ prints that map as JSON
instead. A hyphen-leading name is a name, not an option: pass it directly or
after ~--~.

~recipe templates --export~ prints the constant table and the derived-key
rules. With ~--name~ and ~--version~ it prints the values those rules produce
for that pair, using the lowercased name for the forge-account defaults and
~system~ for the toolchain. ~recipe hierarchy~ prints the known toolchain
generations as JSON. ~--export~ is accepted and prints the same table.

~recipe lint~ prints JSON with ~clean~, ~style~ (each finding carries
~path~, ~line~, ~column~, ~code~, ~severity~, ~message~, and, when set,
~info~ and ~in_review~), ~check_contrib~,
and ~maintainer_acceptability~. It does not rely on ~eb --check-contrib~.
Style codes: E999 (not valid Python; the AST rules are skipped); the
easyconfigs CI lint F541 (f-string with no placeholder), W605 (invalid escape
sequence), and W291 (trailing whitespace, including inside ~description~);
the check-contrib pycodestyle codes E501 (longer than 120) and
E225/E226/E227/E228/E231; the easyconfigs test-suite checks
~EB_PY_NO_USER_SITE~, ~EB_SANITY_PATHS_SHAPE~, ~EB_LOCAL_VAR_NAMING~,
~EB_REDEFINED_PARAM~, and ~EB_CHECKSUM_COUNT~; and the review conventions
~EB_FMT_MISSING_F~, ~EB_FSTRING_QUOTE_REUSE~, ~EB_TEMPLATE_UNKNOWN~ (errors)
and ~EB_FMT_PERCENT~, ~EB_FMT_CONCAT~, ~EB_FMT_TEMPLATE_VAR~,
~EB_SHLIB_HARDCODED~, and ~EB_DEP_DUPLICATE~ (warnings).
~clean~ is false while any error or any in-scope ~EB_FMT_*~ finding
remains; ~error_free~ counts errors only. An ~EB_FMT_*~ finding with
~info~ true is outside the review scope (an untouched ~%%(...)s~-escaped
entry or, with ~--base~, a line unchanged from the base) and does not count.
With ~--base~ the diff-mode rules also run: ~EB_SANITY_ENTRY_REMOVED~ and
~EB_EASYBLOCK_CHANGED~ (errors), ~EB_SANITY_PATHS_REMOVED~ (warning), and
~EB_FMT_TEMPLATE_REMOVED~. ~EB_FSTRING_ESCAPED_TEMPLATE~ and
~EB_DEP_EMPTY_VERSION~ are errors. With ~--base~, the file
before the edit, it also reports ~EB_FMT_TEMPLATE_REMOVED~ where a template
was replaced by a Python expression. ~f'lib/%(name)s.{SHLIB_EXT}'~ is correct
and not flagged. When ~eb~ is on ~PATH~, the command also runs
~eb --check-contrib~ and merges those findings (~origin~ is
~eb --check-contrib~). A missing ~eb~ is reported in ~check_contrib~ and does
not by itself fail the command. Error-severity findings do; warnings do not. ~recipe format~ only wraps mechanical E501 lines; the other codes stay in
~remaining~.

~recipe check~ refuses a recipe that is not valid Python. It prints the
structured dependency result and fails when package
metadata, checksum structure, required configuration flags, or robot
dependencies are invalid. Missing dependencies remain explicit work; the
command does not create placeholder recipes.

~--require-configopt~ takes the flag as it appears in ~configopts~, dashes
included (~--require-configopt --with-tests~). ~--strict~ lists every
statement that failed to parse and fails when that list is not empty.
~if~, ~for~, ~import~, and the other control keywords stay unreported:
that is the tolerant skip, not a parse failure.
~--verify-sources~ classifies each source URL and, with ~--seeded-from~,
rejects a checksum copied from a different artifact class. ~--seeded-source-url~
and ~--seeded-git~ require ~--seeded-from~, which itself requires
~--verify-sources~. ~--source-tree~ compares the version the unpacked tree
declares with the recipe version.

It also prints ~easyblock_resolution~: the class the recipe resolves to
(named, or derived from the software name), the file that defines it, its
bases and its ~extra_options~ keys. A bundle's own ~easyblocks/~ directory,
beside the ~easyconfigs/~ tree the recipe sits in, is searched first. Naming
~--easyblocks~ roots, such as an easyblocks checkout, asserts that the set is
complete: a software-specific ~EB_~ class found in none of them fails the
check with the message EasyBuild would stop on.

~recipe format~ only performs deterministic physical-line wrapping. Product
configuration, source selection, checksums, patches, and sanity paths remain
authored content.

* Stack commands

#+begin_src bash
eb-stack stack solve \
  --easyconfigs TREE [--easyconfigs OVERLAY]... \
  (--stack-policy POLICY.json | --toolchain NAME/VERSION \
   [--root NAME]... [--roots-from-build-list LIST]...) \
  [--baseline-easyconfigs TREE] \
  [--baseline-toolchain-version VERSION] \
  [--baseline-easystack EASYSTACK.yml]... [--baseline-commits-from EB_REPO] \
  [--baseline-also-toolchain NAME/VERSION]... \
  [--filter-deps NAME,NAME...] \
  [--lock-out stack.lock.json] \
  [--sbom-out stack.cdx.json] \
  [--build-list-out build.list] [--build-list-excludes-baseline] \
  [--jenkins-build-list-out next.list [--jenkins-flags-from previous.list]... \
   [--jenkins-gpu-systems gpu-a,gpu-b] [--jenkins-roots-only]] \
  [--stack-diff-out stack.diff.md]

eb-stack stack sbom --lock stack.lock.json [--out stack.cdx.json]

eb-stack stack order \
  --easyconfigs TREE [--easyconfigs OVERLAY]... \
  --root NAME [--root NAME==VERSION]... \
  [--out build-order.txt] \
  [--oldest] \
  [--easystack-out order.yml] \
  [--hashes-out hashes.txt]

eb-stack stack easystack \
  --lock stack.lock.json \
  [--out stack.yml] \
  [--option FILE.eb:OPTION=VALUE]...

eb-stack stack sections \
  LIST --from PREVIOUS.list --out GROUPED.list \
  [--unfiled "New in this generation"]
#+end_src

~stack sbom~ reads the easyconfigs the lock names. A runtime dependency
that is also selected is a CycloneDX ~dependsOn~ edge. A builddependency
is the component property ~eb_stack:buildDependsOn~. ~stack solve --sbom-out~
writes that same document, checksums included. The MCP tool
~eb_stack_sbom~ writes it too. An unreadable path contributes no edge.

~stack solve~ is the multi-root EasyBuild stack solver. Package-profile stack
preferences use the TOML schema documented with the package workflow; whole
stack solving uses the JSON ~Policy~ schema. The policy file is
~--stack-policy~, the same flag ~package plan~ and ~package bump~ take.
~--policy~ is that flag as well.

The baseline is either a previous generation (~--baseline-easyconfigs~, by
default the first ~--easyconfigs~ tree) or what a set of easystacks installs
(~--baseline-easystack~, repeatable). An easystack baseline is every entry
plus the closure its recipes pin, read from the ~--easyconfigs~ trees and kept
to the policy toolchain's hierarchy. An entry pinned with ~from-commit~ is read
from that commit of ~--baseline-commits-from~ when given, and matched by
filename otherwise. Entries that name no recipe are listed on standard error.
~--baseline-also-toolchain~ keeps another family's hierarchy in the baseline,
such as ~lfoss/2026.1~ beside a ~foss/2026.1~ solve. ~--filter-deps~ drops each named dependency before the solve, together
with the subtree under it, using EasyBuild's matching: a bare name,
~name=version~, or ~name=[low:high]~. ~[~ and ~]~ include a limit, the
opposite bracket excludes it, and an empty side is open. The last spec for
a name wins. Pass EESSI-extend's ~EASYBUILD_FILTER_DEPS~ list when solving
against an EESSI baseline, or the build list carries modules the compat
layer already provides.
Against an EESSI version's easystacks, ~unchanged~ in the stack diff means the
software layer already provides that module, and
~--build-list-excludes-baseline~ drops those modules (same name, version,
toolchain and versionsuffix) from the build list, leaving what the site layer
builds on top in dependency order.

A Jenkins build list is one easyconfig filename per line with optional ~eb~
flags, ~#~ for comments. ~--roots-from-build-list~ takes the package name of
every line as a root. ~--jenkins-build-list-out~ writes the solved build order
in that format; each package keeps the ~--hook~, ~--hooks~,
~--include-easyblocks~ and ~--accept-eula-for~ flags of its last line in the
~--jenkins-flags-from~ lists, while flags tied to the old recipe
(~--from-commit~, ~--from-pr~, ~--ignore-test-failure~, ~--rebuild~) stay
behind. A module whose name or versionsuffix says CUDA gets
~--include-systems~ with the ~--jenkins-gpu-systems~ list.
~--jenkins-roots-only~ writes one line per root application and leaves the
dependencies to ~eb --robot~. ~stack sbom --lock~ re-reads the easyconfigs
named in the lock and restores their runtime ~dependsOn~ edges.

~stack order~ sequences the recipes the roots pin. It does not pick one
version per name, so two builds of one name both appear and stdout reports
~multiple builds of NAME~. ~--oldest~ takes the oldest admissible version of
an unpinned requirement. ~--easystack-out~ writes that build order.
~--hashes-out~ writes one ~hash  name-version-toolchain~ line per module.
~stack easystack~ writes the lock, which is sorted by package name, as the
easystack ~eb --easystack~ consumes. ~--option~ is
~<file.eb>:<option>=<value>~. ~stack sections~ regroups a Jenkins list under
the ~#### Title ####~ headers of a previous list. Commented entries stay
commented. A name no previous section files goes under ~--unfiled~, whose
default is ~New in this generation~.

~stack order~ keeps every build the recipes pin. A name the generation
builds twice stays twice, in an order that respects every dependency.
~stack solve~ picks one version of that name; this command does not.
~--root~ repeats, and ~name==version~ pins one build. ~--oldest~ takes the
oldest admissible version of an unpinned requirement. The default is the
newest. ~--out~ is one easyconfig path per line (default
~build-order.txt~). ~--easystack-out~ writes that same sequence as an
easystack. ~--hashes-out~ writes one line per module, ~<sha256>  <module>~,
a digest of the easyconfig and of the hashes of everything it needs. A
module whose recipe could not be read is still listed, and the stdout line
~incomplete=~ counts those. Stdout ends with ~order=<path> builds=<N>~.
A name with two builds also prints ~multiple builds of <name>:~.

~stack easystack~ writes ~easyconfigs:~ as a YAML list of filenames, in
lock order. ~--option~ repeats. The option is spelled as on the ~eb~
command line without its dashes, for example
~--option CUDA-12.8.0.eb:accept-eula-for=CUDA~. A file with options is a
mapping; a file without them is a string. Stdout is
~easystack=<path> entries=<N> of=<packages>~.

Those filenames stay in lock order. ~stack sections~ reads ~LIST~ and
regroups its entries under the
~#### Title ####~ headers of ~--from~. Each entry keeps its flags and
whether it is commented out. Packages no section of ~--from~ names go
under ~--unfiled~ (default ~New in this generation~), last. The comment
block before the first entry of ~LIST~ stays on top. Stdout is
~list=<path> sections=<written> of=<previous+1>~. The ~of~ count is the
previous list's section count plus the unfiled header.

* ~pr-overlap~

#+begin_src bash
eb-stack pr-overlap \
  --pr PR.json [PR.json...] [--pr PR.json]... \
  --easyconfigs TREE [--easyconfigs TREE]... \
  [--commit-tree COMMIT=DIR]... \
  --installed installed.txt \
  [--eessi-version 2026.06] \
  [--installed-label LABEL] \
  [--exclude-path SUBSTR]... \
  [--include-path SUBSTR]... \
  [--filter-deps SPEC,SPEC...] \
  [--installed-modulerc PATH]... \
  [--easyblocks DIR]... \
  [--easyblocks-commit COMMIT=DIR]... \
  [--generated-at RFC3339] \
  [--merge-order] \
  [--merged N]... \
  [--repo-url URL] \
  [--out-dir pr-overlap]
#+end_src

Reads each pull request's easystack changes as data. It does not run the
pull request and it does not build. Several JSON paths may follow one
~--pr~, which is what a glob of the per-pull-request files expands to.
For the given ~--eessi-version~ it keeps
the easystack entries present at head and absent from base, finds those
easyconfigs on the robot path, and closes them against ~--installed~.

~--easyconfigs~ is the release robot tree. Later trees win on the same
name, version, toolchain, and versionsuffix. ~--commit-tree~ is the
easyconfigs tree at one ~from-commit~, and it wins over the release tree for
entries pinned to that commit.

~--exclude-path~ drops easystack paths that contain the substring.
~--include-path~, when given, keeps only paths that contain one of the
substrings. An empty include list keeps every path that survived the
excludes.

An installed module is a leaf. Entries under a ~rebuilds/~ easystack are
built even when installed. A requirement no easyconfig satisfies is recorded
and the rest of the closure is still written.

~--filter-deps~ is comma-separated and uses the same matching as
~stack solve~. A filtered dependency is dropped before the walk, so the
modules reachable only through it are never opened. When the flag is omitted
and ~EASYBUILD_FILTER_DEPS~ is set, that value is used. A non-empty flag
wins over the environment.

~--installed-modulerc~ is a ~.modulerc.lua~ file or a module tree. A
~module_version("Name/full", "alias")~ line makes ~Name/alias~ installed
when ~Name/full~ is on the installed list.

~--easyblocks~ is the installed ~easybuild/easyblocks~ package. Passing any
root checks every easyblock class. A software-specific class none of the
roots defines is recorded as ~easyblock <class> missing~ and that module is
left out of ~to_build~. Its dependencies stay. ~--easyblocks-commit~ is
~<commit>=<dir>~ for one ~include-easyblocks-from-commit~: the directory is
the easyblock files that commit touches, which is what EasyBuild includes
ahead of the installed package. A class found there is counted, and the
record notes the commit. A commit an entry names whose directory was not
passed is noted as not provided.

~--kind~ selects the pull request shape. ~software-layer~ is the default
and reads easystack additions. ~easyconfigs~ reads changed ~.eb~ files.
~--installed~ is required for ~software-layer~. For ~easyconfigs~ it is
optional: with the flag, ~to_build~ is the closure minus that list; without
it, ~to_build~ is the modules the base tree does not provide.
~--eessi-version~ is ignored for ~easyconfigs~ and is omitted from the
record. ~--repo-url~ defaults to
~https://github.com/EESSI/software-layer~ for ~software-layer~ and to
~https://github.com/easybuilders/easybuild-easyconfigs~ for ~easyconfigs~.

* ~rebuild-set~

#+begin_src bash
eb-stack rebuild-set \
  --changed FILE.eb [--changed FILE.eb]... \
  --easystack STACK.yml [--easystack STACK.yml]... \
  --easyconfigs TREE [--easyconfigs TREE]... \
  [--commit-tree COMMIT=DIR]... \
  --installed installed.txt \
  [--installed-label LABEL] \
  [--filter-deps SPEC,SPEC...] \
  [--installed-modulerc PATH]... \
  [--easyblocks DIR]... \
  [--easyblocks-commit COMMIT=DIR]... \
  [--generated-at RFC3339] \
  [--prefix "$EESSI_SOFTWARE_PATH"] \
  [--check-static] \
  [--out-dir rebuild-set]
#+end_src

Resolves the deployed easystacks and the installed reverse dependents of
each patched easyconfig. The patch keeps the filename and the version.
Classification starts from the easyconfig graph. The closure stays inside
the patched module's toolchain generation: an unpinned dependency is
resolved in the dependent's own generation, and a module from another
generation is not a row.

~--changed~ is an easyconfig filename. Repeat it, or pass a file that does
not end in ~.eb~: one filename per line, blank lines and ~#~ comments
skipped. The basename is what is matched. A filename that is not in the
deployed graph is listed under ~missing~ and has no row.

~--easystack~ is a deployed easystack, repeated. Every entry is a root.
~--easyconfigs~, ~--commit-tree~, ~--installed~, ~--filter-deps~,
~--installed-modulerc~, ~--easyblocks~, and ~--easyblocks-commit~ mean the
same as for ~pr-overlap~. ~--filter-deps~ drops dependency tuples and does
not strip ~exts_list~. A missing easyblock class is recorded and the
module stays, because it is already installed.

A runtime dependency is ~no-rebuild~. A dependent reached only through
builddependencies is ~review~. The patched easyconfig, and a bundle whose
~exts_list~ names that package and version, are ~must-rebuild~. A toolchain
edge is not classified. A review dependent is one row, and ~changed~ lists
every patched easyconfig that put it there. See
[[file:../explanation/rebuild-set.org][what an in-place patch forces a rebuild of]].

~--prefix~ reads ~software/<name>/<version>/lib*/*.a~. No static archive
makes a builddependency-only dependent no-rebuild, with the reason ~no
static archive installed~. Archives that are installed keep the row in
review and are named. A missing install directory is a note.

~--check-static~ needs ~--prefix~. It compares defined dynamic symbols of
the remaining review dependents with the patched library's exports. A hit
is must-rebuild. No hit is no-rebuild. An empty export set stays in
review. The scan sees dynamic symbols only, so a hidden or inlined static
link is a false no-rebuild, and a short name shared with another library
is a false must-rebuild.

The output directory holds ~rebuild-set.json~, ~rebuild-set.md~, and
~rebuilds/<YYYYMMDD>-eb-<version>-cve-patches.yml~. The easystack contains
class ~must-rebuild~ only, including a dependent that ~--check-static~
promoted. A second run replaces the ~rebuilds/*.yml~ files.

* ~component-reach~

#+begin_src bash
eb-stack component-reach \
  (--component NAME --version VER | --purl PKG:TYPE/NAME@VER | --cve CVE-ID) \
  --generation 2026.1 \
  --easyconfigs TREE [--easyconfigs TREE]... \
  [--installed installed.txt] \
  [--easystack STACK.yml]... \
  [--easystack-url https://.../STACK.yml]... \
  [--compat-layer FILE] \
  [--filter-deps SPEC,SPEC...] \
  [--generated-at RFC3339] \
  [--out-dir component-reach]
#+end_src

Lists every easyconfig and installed module in one toolchain generation
that carries a component, then feeds the recipes that contain it into
the rebuild closure. See
[[file:../howto/component-reach.org][which modules carry a component]].

Pass ~--component~ and ~--version~, or ~--purl~, or ~--cve~. ~--version~
is an exact version, ~*~, or a requirement such as ~>=8,<9~. With
~--purl~ it replaces the version in the URL. ~--cve~ resolves the id
through OSV, follows GHSA, RUSTSEC, PYSEC, and GO aliases when the CVE
record has only a git range, and keeps named version tags such as
~libXpm-3.5.17~. Several affected packages are written as one document
with ~kind~ ~cve~.

Names match with ASCII case folded, on a whole token. A recipe is in the
generation when its toolchain version equals ~--generation~, or when the
toolchain is a non-system member of the known foss hierarchy for that
generation.

A hit is a dependency or builddependency tuple, a bundle ~components~
entry, an ~exts_list~ extension, a Cargo crate (a ~crates~ tuple, a
filename such as ~libz-sys-1.1.29.tar.gz~, or a checksum key such as
~rustls-webpki-0.102.8.tar.gz~), a Python wheel (~.whl~ in ~sources~,
~checksums~, an ~exts_list~ source, or ~source_tmpl~), or a versioned
name in ~sources~ or ~patches~. A ~+name-version~ fragment inside a crate
version counts as that vendored version. The recipe's own tarball is not
a crate it carries. A dependency or builddependency is a carrier and
is not a patched root. The other roles are: the recipe contains the
component, and its filename is a changed input of the closure.

~--easystack-url~ repeats and must be ~https://~. It is read the same
way as ~--easystack~.

~--compat-layer~ is ~name version~ or ~name==version~ per line, ~#~
comments skipped. The compat layer is not an easyconfig, so a hit has an
empty easyconfig and a note, and it is not a closure edge.
~--filter-deps~ matches ~rebuild-set~ and reads ~EASYBUILD_FILTER_DEPS~
when the flag is omitted. It does not strip ~exts_list~.

With no ~--easystack~, every easyconfig in the generation is the stack.
With no ~--installed~, every module in the generation is treated as
installed. Pass both to visit only a mounted prefix. The closure classes
are the same as ~rebuild-set~, and they stay inside the generation.

The output directory holds ~component-reach.toml~, ~component-reach.json~,
and ~component-reach.md~. The TOML file starts with
~# Generated by `eb-stack component-reach`.~

* Target commands

#+begin_src bash

eb-stack target doctor \
  --config BASE.toml [--config SITE.toml]... \
  --target NAME
#+end_src

Target layers are applied in argument order. A complete target contains:

- transport: local or SSH;
- executor: direct or Slurm;
- runtime: host, Podman, or Docker;
- EasyBuild workload: command, robot paths, work root, temporary root, and
  environment.

~target doctor~ probes each layer separately and reports the exact routed
command, exit code, stdout, and stderr.

See [[file:targets.org][build target configuration]] for complete layer schemas,
replacement semantics, ABI isolation, and the runnable local Podman target.

* Campaign commands

#+begin_src bash
eb-stack campaign run \
  --bundle BUNDLE \
  --config BASE.toml [--config SITE.toml]... \
  --target NAME \
  --state CAMPAIGN.json

eb-stack campaign status --state CAMPAIGN.json

eb-stack campaign finding claim \
  --state CAMPAIGN.json --id FINDING --owner WORKER

eb-stack campaign finding resolve \
  --state CAMPAIGN.json --id FINDING --owner WORKER \
  --action TEXT --evidence TEXT [--change PATH]...
#+end_src

~campaign run~ resumes state with matching package identity, increments the
attempt, stages the bundle, runs every emitted recipe, and executes each
profile's verification commands. Transport, executor, runtime, interrupted,
checksum, patch, dependency, configure, compile, link, test, install, sanity,
resource, timeout, and unknown failures are persisted as typed findings.

Finding claims are exclusive. A resolution records an action, evidence, and
changed paths. A successful retry supersedes matching open or in-progress
findings. Campaign state reports ~resolves~, ~builds~, and ~binary_verified~
independently.

See [[file:campaigns.org][campaign state and typed findings]] for the serialized
state, claim ladder, class/disposition table, and repair protocol.

* ~repro summary~

#+begin_src bash
eb-stack repro summary \
  --scores DIR \
  [--ratchet ratchet.json] \
  [--json]
#+end_src

Reads every ~*.json~ case score the reproduction suite wrote under
~--scores~ (the directory ~EB_REPRO_SCORES~ points at when the suite runs)
and prints the scoreboard table:

#+begin_src text
| Case | PR | Score | Allowance | Residual |
|---+---+---+---+---|
| reproduces_gromacs | - | EXACT | 1 | 0 |

2 cases: 1 EXACT, 1 SEMANTIC, 0 MATERIAL; allowance total 1
#+end_src

~Score~ is ~EXACT~, ~SEMANTIC~, or ~MATERIAL~. ~Allowance~ is how many
hand-added lines the case still forgives. ~Residual~ is the raw diff lines
left after that allowance. A pull request number prints as ~#N~; a case
with none prints ~-~. ~--json~ prints the case records instead of the
table: ~case~, ~pull_request~, ~source~, ~target~, ~score~, ~allowance~,
~stale_allowance~, ~residual_lines~. ~--ratchet~ reads
~{"note", "cases", "total"}~. ~--ratchet~ exits nonzero when a case's
allowance disagrees with the committed count, when a case is missing from
the file, or when ~total~ is not the sum of ~cases~. A matching run also prints
~ratchet: <N> cases hold at <total>~. An empty ~--scores~ directory is an
error. See [[file:../explanation/fidelity.org][reproduction fidelity]].

* MCP

#+begin_src bash
eb-stack mcp [--workspace ROOT]
#+end_src

~--workspace~ sets ~EB_STACK_WORKSPACE~ for the recipe file tools. When it is
omitted, an existing ~EB_STACK_WORKSPACE~ is kept, and otherwise the server's
current directory is the root.

The stdio server exposes one MCP tool for each of these CLI workflows,
plus sandboxed recipe and easyblock tools:

- ~eb_package_inspect~, ~eb_package_plan~, ~eb_package_bump~;
- ~eb_recipe_read~, ~eb_recipe_list~, ~eb_recipe_edit~, ~eb_recipe_write~,
  ~eb_recipe_grep~, ~eb_recipe_apply_suggestion~, ~eb_recipe_diff~,
  ~eb_dep_versions~;
- ~eb_recipe_check~, ~eb_recipe_lint~, ~eb_recipe_format~;
- ~eb_module_lint~, ~eb_easyblock_dry_run~, ~eb_build_log~, ~eb_build_test~
  (easyblocks; ~eb_build_test~ only with ~EB_STACK_ALLOW_BUILD=1~);
- ~eb_stack_solve~, ~eb_stack_sbom~;
- ~eb_target_list~, ~eb_target_doctor~;
- ~eb_campaign_run~, ~eb_campaign_status~;
- ~eb_campaign_finding_claim~, ~eb_campaign_finding_resolve~;
- ~eb_pr_overlap~ (~kind~ ~software-layer~ or ~easyconfigs~),
  ~eb_rebuild_set~, ~eb_component_reach~, ~eb_easyblock_reach~.

~eb_recipe_read~, ~eb_recipe_list~, ~eb_recipe_edit~, ~eb_recipe_write~, and
~eb_recipe_grep~ resolve every path inside that root. A ~..~ component, an
absolute path outside the root, or a symlink whose target leaves the root is
rejected and the file is not opened. ~eb_recipe_edit~ replaces an exact
string. If ~old~ matches more than once, the file is left unchanged unless
~replace_all~ is true. ~eb_recipe_write~ does not create parent directories.
~eb_recipe_grep~ searches for a literal ~pattern~ (a regular expression when
~regex~ is true) under ~path~ (default the root), skips ~.git~, does not
follow symlinks, and returns at most ~max_matches~ (default and limit 200)
matches. ~eb_recipe_check~ requires ~easyconfigs~ (~minItems~ 1). An empty
list returns ~argument easyconfigs requires at least one path~. A ~.eb~ file
there stands for the ~easyconfigs~ directory it sits in; any other file is an
error that asks for a robot directory. A recipe that is not valid Python is
refused. It also takes ~recipe~, ~require_configopts~, ~easyblocks~,
~metadata_only~, ~verify_sources~, ~seeded_from~, ~seeded_source_url~,
~seeded_git~, ~source_tree~, and ~strict~, and returns maintainer
acceptability, easyblock resolution, strict skips, and source classes.
~eb_recipe_lint~ takes a ~recipes~ path array and returns ~results~ plus
~check_contrib~, using the same findings and maintainer-acceptability as
~recipe lint~. ~eb_recipe_format~ takes ~recipe~, ~out~, and ~dry_run~, and a
dry run does not write.

The recipe tools run the same checks as the CLI. MCP results include the same
artifacts, claims, findings, and next actions as the CLI. There is no separate
compatibility command surface.

~eb_package_plan~ accepts the CLI's repeated source-checksum input as a
~source_checksums~ string array, and the catalog / source-root inputs as
~package_catalogs~, ~package_sources~, ~easybuild_sources~, ~conda_sources~,
~spack_sources~, and ~cargo_sources~ arrays. ~emit_easyblock~ asks for an
easyblock skeleton in the bundle and does not combine with package-closure
planning. ~eb_package_plan~ also takes ~package_index~, a CRAN
~PACKAGES~ file or a ~name==version~ list, the same input as
~--package-index~. ~eb_package_bump~ optionals include ~version~,
~source_checksum~, ~dependencies~ (object map), ~hierarchy_fixture~,
~stack_policy~, ~package_configs~, ~emit_easyblock~, ~fetch_checksums~,
~strict_patches~, and ~toolchain~ (~name/version~). ~toolchain_name~ and
~toolchain_version~ are required when ~toolchain~ is absent.
~strict_patches~ fails the bump when a patch's fate cannot be decided,
as ~--strict-patches~ does. ~fetch_checksums~ downloads the new source
and writes its SHA-256, as ~--fetch-checksums~ does.
~eb_package_inspect~ and ~eb_package_plan~ take that same ~toolchain~
spelling, and default a missing ~toolchain_name~ to ~foss~.
~eb_stack_solve~ reads the policy file as ~stack_policy~. ~policy~ is
that argument as well.
~eb_recipe_lint~ takes a ~recipes~ path array, or a single ~recipe~ path, and returns
reviewer-style findings plus ~check_contrib~. ~eb_campaign_finding_resolve~
takes ~changes~ as an optional path array. ~eb_recipe_check~'s
~easyconfigs~ array has ~minItems~ 1. ~eb_recipe_read~, ~eb_recipe_list~,
~eb_recipe_edit~, and ~eb_recipe_write~ edit files only inside the workspace
root.
