#+TITLE: Run an annual toolchain-generation bump
#+OPTIONS: toc:t num:nil

The annual workflow applies the canonical bump bundle to each maintained
recipe, then drives every bundle through the same target-routed build campaign.
Dependency version selection is mechanical; build failures remain typed repair
work.

* Prepare the generation inputs

Record:

- the source and target toolchain generations;
- upstream EasyBuild robot roots and site overlays;
- the stack-policy TOML for site/distribution preferences;
- the public target base plus the site target layer;
- the maintained recipe list and destination easyconfigs repository.

The site layer owns hostnames, scheduler sizing, module setup, durable build
paths, container images, and environment. Do not put those values in the
public skill.

* Generate one canonical bundle per recipe

#+begin_src bash
eb-stack package bump \
  --source tests/repro_fixtures/gromacs/GROMACS-2024.4-foss-2023b.eb \
  --toolchain-name foss \
  --toolchain-version 2024a \
  --easyconfigs tests/repro_fixtures/universe_foss_2024a \
  --out-dir /tmp/eb-stack/bundles/gromacs-2024a
#+end_src

Repeat mechanically for the maintained set. Each successful bundle contains a
manifest, planned SBOM, default profile lock, and recipe. The lock records stack
pin fallbacks and exclusions, making generation policy reviewable.

Explicit dependency toolchain families are retargeted with the parent
generation: a ~gfbf-2023b~ dependency in a source recipe becomes a
~gfbf-2024a~ solver requirement in this example. Implicit tuples stay implicit
when Resolvo selects a dependency within the target hierarchy. A locked or
preferred cross-generation pin is emitted as an explicit four-element
EasyBuild tuple so the generated recipe records the artifact identity that the
lock selected.

* Validate generated recipes

#+begin_src bash
eb-stack recipe format /tmp/eb-stack/bundles/gromacs-2024a/easyconfigs/g/GROMACS/*.eb
eb-stack recipe lint /tmp/eb-stack/bundles/gromacs-2024a/easyconfigs/g/GROMACS/*.eb

eb-stack recipe check \
  --recipe /tmp/eb-stack/bundles/gromacs-2024a/easyconfigs/g/GROMACS/GROMACS-2024.4-foss-2024a.eb \
  --easyconfigs tests/repro_fixtures/universe_foss_2024a \
  --easyconfigs /tmp/eb-stack/bundles/gromacs-2024a/easyconfigs
#+end_src

Resolve missing dependencies by adding a real package bundle or authored recipe.
Checksums are positional: all sources first, then patches. Fix recipe content;
never bypass the packaging gate.

* Solve the multi-root stack

Use ~stack solve~ when the campaign also needs a generation-wide lock, build
list, or baseline diff:

#+begin_src bash
eb-stack stack solve \
  --easyconfigs fixtures/gromacs_2025_to_next/easyconfigs \
  --policy fixtures/gromacs_2025_to_next/policies/prefer_newer.json \
  --baseline-easyconfigs fixtures/gromacs_2025_to_next/easyconfigs \
  --lock-out /tmp/annual-stack.lock.json \
  --sbom-out /tmp/annual-stack.cdx.json \
  --build-list-out /tmp/annual-build.list \
  --stack-diff-out /tmp/annual-stack.diff.md
#+end_src

The whole-stack policy and package stack-policy solve related but distinct
problems: JSON chooses a multi-root stack; TOML controls preferred/locked pins
and exclusions for one generated product profile.

* Validate target routing

#+begin_src bash
podman build -t eb-stack-rocky9 \
  -f skills/new-package/container/rocky9/Containerfile \
  skills/new-package/container/rocky9

eb-stack target doctor \
  --config examples/targets/local-podman.toml \
  --target local-rocky9
#+end_src

The doctor must show healthy transport, executor, runtime, and EasyBuild
workload checks before a campaign claim is trusted.

* Drive every build campaign

#+begin_src bash
eb-stack campaign run \
  --bundle /tmp/eb-stack/bundles/gromacs-2024a \
  --config examples/targets/local-podman.toml \
  --target local-rocky9 \
  --state /tmp/eb-stack/bundles/gromacs-2024a.campaign.json
#+end_src

Hermes owns the retry loop. OMP workers claim findings and repair according to
class:

| Class | Repair surface |
|-
| transport / executor / runtime | target or site configuration |
| checksum | source digest and positional checksum list |
| patch | patch source or applicability |
| dependency-missing | manifest, profile, stack policy, or real dependency recipe |
| configure / compile / link | product configuration, toolchain, patch, or dependency selection |
| test / install / sanity | recipe build logic and verification |
| resource / timeout | scheduler sizing or retry policy |

Each resolution records action, evidence, and changed paths. Rerun the same
campaign state; successful stages supersede stale open findings.

* Report claims accurately

- *resolves* means every requested profile has a lock and recipe.
- *builds* means every emitted recipe succeeds through EasyBuild on the target.
- *binary-verified* means every declared verification command succeeds.

An annual bump is not complete while an affected campaign remains failed or a
required verification command is absent. The human operator owns branch/PR
publication; the campaign supplies the recipe set and evidence.

The executable procedure is ~skills/annual-bump/SKILL.md~.
