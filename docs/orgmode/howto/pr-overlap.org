#+TITLE: Find shared builds across open pull requests
#+OPTIONS: toc:t num:nil author:nil

Goal: for every open pull request that changes an easystack, write what it
would build on the current stack, and which of those modules more than one
open pull request would build.

The inputs are the pull requests' easystack files, the release easyconfigs,
and a list of installed modules. Nothing from a pull request is executed.

* Run it on the recorded pull requests

~tests/pr_overlap_layer/~ records pull requests 1585 and 1728 from
European Environment for Scientific Software Installations (EESSI) software-layer ~b2c10c7278f8b741f4053ddb2907dc4d062063d1~. Both
change
~easystacks/software.eessi.io/2026.06/eessi-2026.06-eb-5.4.0-2026.1.yml~.
1585 adds ~SciPy-bundle-2026.05-gfbf-2026.1.eb~. 1728 adds
~PLUMED-2.10.0-foss-2026.1.eb~, and that recipe depends on SciPy-bundle
2026.05. The easyconfigs are the 109 modules the two closures reach,
copied from easybuild-easyconfigs develop
~981d2123dddccca9ce0b15f9eb2643e872332f5e~. ~installed.txt~ is a comment,
because this checkout has no mounted prefix.

The 1585/1728 pair is a replay of a recorded state. Pull request 1585
merged on 2026-09-04. The recorded base of 1728 already lists
~SciPy-bundle-2026.05-gfbf-2026.1.eb~. The two used different bases.
The command replays 1728's easystack against an empty ~installed.txt~,
which is why the pair shares 91 modules. To run the same command on
live pull requests, clone ~EESSI/software-layer~, write one JSON file
per open pull request with ~examples/eessi-pr-overlap/fetch-prs.sh~,
and pass the prefix's installed module list. The next section is that
run.

#+begin_src bash
eb-stack pr-overlap --pr tests/pr_overlap_layer/prs.json \
  --easyconfigs tests/pr_overlap_layer \
  --installed tests/pr_overlap_layer/installed.txt \
  --installed-label none \
  --generated-at 2026-10-24T00:00:00Z \
  --repo-url https://github.com/EESSI/software-layer \
  --eessi-version 2026.06 \
  --merge-order \
  --out-dir /tmp/pr-overlap-out
#+end_src

The command prints ~prs=2 records=2 shared_modules=91 skipped_easyconfigs=0~.
~--merge-order~ writes ~/tmp/pr-overlap-out/merge-order.toml~. Position 1
is pull request 1585, which builds the 91 modules. Position 2 is pull
request 1728, which builds the remaining 18 once 1585 is first, and
~after~ is 1585.

~fetch-prs.sh~ lives in this repository at
~examples/eessi-pr-overlap/fetch-prs.sh~. It writes one JSON file per open
pull request from a clone. Pass those files as repeated ~--pr~ arguments,
and pass ~--commit-tree NAME=DIR~ and ~--easyblocks-commit NAME=DIR~ for
each directory it wrote. ~--easyconfigs~ is the easyconfigs tree that comes
with the EasyBuild version the easystack names. ~--installed-modulerc~
is that prefix's ~modules/all~. ~--filter-deps~ drops dependencies the
way EasyBuild does; when the flag is omitted and ~EASYBUILD_FILTER_DEPS~
is set, the command reads the variable.

For a ~from-commit~ pin, ~--commit-tree~ is the whole easyconfigs tree at
that commit. ~--easyblocks~ is the EasyBuild release's
~easybuild/easyblocks~ package. ~--easyblocks-commit~ is the files one
~include-easyblocks-from-commit~ touches.

For another architecture, pass that architecture's installed list and
~--include-path~ for its substring. Do not also exclude the same
substring. ~--installed-label~ is the string recorded on the report.
That is still one added-lines closure. The bot's whole-file build set,
one per architecture, is
[[*What the bot builds on each architecture][what the bot builds on each architecture]].

* Run it on a mounted stack

From a clone of ~EESSI/software-layer~, with ~gh~ authenticated for public
reads. ~EB_EASYCONFIGS~ and ~EB_EASYBLOCKS~ come from
~scripts/fetch-upstream-trees.sh~. ~examples/eessi-pr-overlap/fetch-prs.sh~
writes one JSON file per open pull request. The outputs go under ~/tmp~
so the checkout stays unchanged.

#+begin_src bash
scripts/fetch-upstream-trees.sh
set -a
source "${EB_UPSTREAM_CACHE:-$HOME/.cache/eb-stack/upstream}/env.sh"
set +a
examples/eessi-pr-overlap/fetch-prs.sh EESSI/software-layer 2026.06 /tmp/pr-overlap-in/
find "$EESSI_SOFTWARE_PATH/software" -mindepth 2 -maxdepth 2 -type d -printf '%P\n' \
  | sort > /tmp/pr-overlap-installed.txt
eb-stack pr-overlap --pr /tmp/pr-overlap-in/prs/*.json \
  $(for d in /tmp/pr-overlap-in/commit-trees/*/; do printf -- '--commit-tree %s=%s ' "$(basename "$d")" "$d"; done) \
  $(for d in /tmp/pr-overlap-in/easyblocks/*/; do printf -- '--easyblocks-commit %s=%s ' "$(basename "$d")" "$d"; done) \
  --easyconfigs "$EB_EASYCONFIGS" \
  --easyblocks "$EB_EASYBLOCKS" \
  --installed /tmp/pr-overlap-installed.txt \
  --installed-modulerc "$EESSI_SOFTWARE_PATH/modules/all" \
  --filter-deps "$EASYBUILD_FILTER_DEPS" \
  --installed-label x86_64/amd/zen4 \
  --generated-at 2026-10-22T00:00:00Z \
  --out-dir /tmp/pr-overlap-out
#+end_src

* Read which modules are shared

~/tmp/pr-overlap-out/prs/<N>.toml~ lists ~to_build~ as one sorted line per
module. Duplicates across those lines are the overlap:

#+begin_src bash
awk '/^to_build = \[\]/{next} /^to_build = \[/{f=1; next} f && /^\]/{f=0; next} f' /tmp/pr-overlap-out/prs/*.toml | sort | uniq -d
#+end_src

On the recorded pair, that list has 91 modules.
~/tmp/pr-overlap-out/overlap.md~ is the same answer as a table. The
SciPy-bundle row names pull requests 1585 and 1728.
~/tmp/pr-overlap-out/overlap.toml~
is the index. Closed pull requests have no file: each run rewrites ~prs/~
to the open set.

* Wire it into CI

The draft workflow is
~examples/eessi-pr-overlap/pr_dependency_overlap.yml~. It is not installed
in ~EESSI/software-layer~ from this repository.

On the software-layer repository:

1. Exempt ~gh_action_pr_dependency_overlap~ from the branch push restriction,
   the same way ~gh_action_update_software_layer_commit_sha~ is exempt, so
   ~github-actions[bot]~ can push to that one branch. ~main~ stays protected.
2. Copy ~pr_dependency_overlap.yml~ to ~.github/workflows/~ and
   ~fetch-prs.sh~ to ~.github/workflows/scripts/fetch_pr_easystacks.sh~.
3. Set ~EB_STACK_VERSION~ and ~EB_STACK_SHA256~ in the workflow to a release
   that carries ~pr-overlap~.

The workflow runs on a schedule and on ~workflow_dispatch~, from ~main~. It
mounts the stack, writes the three output files, and pushes them to
~gh_action_pr_dependency_overlap~ without force. It opens no pull request
and posts no comment. The publish job commits only when a build set changed.
A timestamp change alone is not committed.

The compute step loads ~EESSI-extend~ and passes ~$EASYBUILD_FILTER_DEPS~,
~--installed-modulerc~, ~--easyblocks~, and one ~--easyblocks-commit~ per
directory ~fetch-prs.sh~ wrote. The filter list is not written into the
workflow file.

Why the files are regenerated on every run, and why a second build of a
shared module overwrites the first binary, is covered in
[[file:../explanation/pr-overlap.org][from one easystack line to a build set]].

* What the bot builds on each architecture

The EESSI bot does not build only the lines a pull request adds. For each
changed easystack it builds every entry at the pull request head that is
not yet installed on the target architecture, and the dependencies of those
entries that are not installed either. An entry can sit in the shared
easystack for months and still be missing on one architecture. The next
pull request that touches the file makes the bot try it again.

~--arch-installed ARCH=FILE~ is that build set. Repeat it once per
architecture. The name before ~=~ is the label in the report. The file is
the same installed-module list as ~--installed~. The flag replaces
~--installed~, and it implies ~--bot-build-set~. Without either flag the
command still closes only the added lines, which is what the recorded
1585/1728 run above does.

~--bot-build-set~ with the existing ~--installed~ list is the same closure
for one architecture. ~to_build~, ~--merge-order~, and ~--impact~ then use
that set. With two or more ~--arch-installed~ values, each architecture has
its own ~to_build~ under ~[[build_sets]]~, and merge order and impact are
computed from those sets.

This recording is the shape of software-layer pull request 1775. The shared
easystack already lists ~GDRCopy-2.5.2-GCCcore-15.2.0.eb~. Pull request 1775
adds ~nvtop~, and pull request 1800 adds ~likwid~. GDRCopy is on the x86_64
installed list and absent from the riscv64 list. Lib is a dependency of
GDRCopy and is installed on neither architecture.

#+begin_src bash
eb-stack pr-overlap \
  --pr tests/pr_overlap_arch/prs.json \
  --easyconfigs tests/pr_overlap_arch/release \
  --arch-installed x86_64=tests/pr_overlap_arch/x86_64.txt \
  --arch-installed riscv64=tests/pr_overlap_arch/riscv64.txt \
  --generated-at 2026-10-30T00:00:00Z \
  --repo-url https://github.com/EESSI/software-layer \
  --merge-order \
  --impact 1775 \
  --out-dir /tmp/pr-overlap-arch
#+end_src

The command prints ~prs=2 records=2 shared_modules=2 skipped_easyconfigs=0~.
~shared_modules~ counts a shared module once per architecture, so both of
those are on riscv64.

~/tmp/pr-overlap-arch/overlap.md~ has one section per architecture. The
x86_64 section's shared table is ~None.~ Pull request 1775 builds
~nvtop/3.3.2-GCCcore-15.2.0~ there and nothing else. The riscv64 section
names the two shared modules:

#+begin_src text
| `GDRCopy/2.5.2-GCCcore-15.2.0` | [#1775](https://github.com/EESSI/software-layer/pull/1775), [#1800](https://github.com/EESSI/software-layer/pull/1800) |
| `Lib/1.0-GCCcore-15.2.0` | [#1775](https://github.com/EESSI/software-layer/pull/1775), [#1800](https://github.com/EESSI/software-layer/pull/1800) |
#+end_src

Under pull request 1775 the report says GDRCopy was already in the changed
easystack and is not installed, and the to-build list is GDRCopy, Lib, and
nvtop. Lib is there because GDRCopy is not installed, so the walk opens it.
On x86_64 GDRCopy is installed, the walk stops, and Lib is not a module to
build.

The same sentence is how you tell an old entry from a line this pull
request added. ~entries~ in ~prs/1775.toml~ is still only the nvtop line.
~carried~ on the riscv64 build set is GDRCopy.

~--merge-order~ appends a table per architecture. On riscv64, position 1 is
1775 and it saves GDRCopy and Lib for 1800. Position 2 is 1800, which then
builds only likwid. On x86_64 each pull request builds its own added module
and saves nothing.

~merge-impact.toml~ is the effect of merging 1775 on its own. On riscv64,
1800 shrinks by GDRCopy and Lib. On x86_64, ~affected~ is empty. Neither
pull request asks for the other's added module, so ~resolves~ is empty on
both architectures.

The same inputs with only ~--installed tests/pr_overlap_arch/riscv64.txt~
and no bot flag leave GDRCopy out of ~to_build~. That is the added-lines
report, and it is not what the riscv64 bot builds.

* Order the merges

~--merge-order~ writes ~/tmp/pr-overlap-out/merge-order.toml~ and appends a
table to ~/tmp/pr-overlap-out/overlap.md~. The command is the one in
[[*Run it on the recorded pull requests][Run it on the recorded pull requests]].
Position 1 is 1585 (91 modules). Position 2 is 1728 (18 modules), and
~after~ is 1585. The rule is in
[[file:../explanation/pr-overlap.org][Merge order and knock-on]].

* What one merge changes

~--impact N~ writes ~/tmp/pr-overlap-out/merge-impact.toml~ and does not
write ~merge-order.toml~. It is the effect of merging N on its own, not
the residual after earlier steps of ~--merge-order~. A number that is not
in the input exits with ~--impact N: no pull request with that number~.
A pull request that is in the input but changes nothing exits with
~--impact N: pull request N has no record (no easyconfigs or easystack change)~.
The recorded command above does not pass ~--impact~.
