#+TITLE: Split a Jenkins build list into shards
#+OPTIONS: toc:t num:nil author:nil

What it does: ~stack shard~ takes one Jenkins build list for one node
type and splits it into shards that can build at the same time. A
line's set is its closure over ~--easyconfigs~ minus the modules that
are already installed. Two lines share a shard only when one line's
easyconfig is in the other's set. Every other module that two or more
shards need goes to ~prelude.list~, which builds first.

Why you'd use it: a site build list for one CPU target is too long for
one job, and a naive split rebuilds HDF5 in every shard. The prelude
holds the shared dependencies once.

* Split the fixture wave

~tests/stack_shard_fixtures/wave1.list~ is four lines: OpenFOAM,
ParaView, PETSc, and Hypre. PETSc depends on Hypre, so those two lines
share a shard and Hypre is first. OpenFOAM and ParaView both need HDF5
and Szip; OpenFOAM and PETSc both need MathLib. Those shared modules
are not lines of their own, so they go to the prelude. zlib is
installed through the module tree and CMake through the installed
list, so neither is built.

#+begin_src bash
eb-stack stack shard \
  --build-list tests/stack_shard_fixtures/wave1.list \
  --easyconfigs tests/stack_shard_fixtures/easyconfigs \
  --installed tests/stack_shard_fixtures/installed.txt \
  --installed-modules-dir tests/stack_shard_fixtures/modules/all \
  --shards 4 \
  --generated-at 2026-11-03T00:00:00Z \
  --out-dir /tmp/shards
#+end_src

That command printed:

#+begin_example
shards=3 prelude=3 lines=4
#+end_example

~/tmp/shards/prelude.list~ is the shared dependencies, in dependency
order:

#+begin_example
Szip-2.1.1-GCCcore-15.2.0.eb
HDF5-1.14.6-GCCcore-15.2.0.eb
MathLib-1.0-GCCcore-15.2.0.eb
#+end_example

The three shard files keep the input lines verbatim. Hypre is a line
PETSc needs, so it is first in that shard:

#+begin_example
Hypre-2.33.0-GCCcore-15.2.0.eb
PETSc-3.23.0-GCCcore-15.2.0.eb --include-easyblocks=/sw/easyblocks/petsc.py
#+end_example

#+begin_example
ParaView-6.0.0-GCCcore-15.2.0.eb
#+end_example

#+begin_example
OpenFOAM-13-GCCcore-15.2.0.eb --hooks=/sw/hooks/openfoam.py
#+end_example

~--shards 4~ is an upper bound. Three groups exist, so three shard
files are written. ~plan.json~ records each line's closure, the shard
weights, and a SHA-256 of the inputs. ~--generated-at~ fixes the time
in that file. ~--weights~ is ~Name/VersionFull~ or the easyconfig
filename, a tab, then seconds. A module the file does not list weighs
~--default-weight~, which is 1. Build the prelude, then the shards.

A line whose easyconfig is not on the robot path exits 1 and writes
nothing. ~eb_stack_shard~ is the same command. See
[[file:../reference/cli.org][the CLI reference]].

* Plan around a scratch inode quota

A native build job keeps its build tree on scratch while it runs, and a
GPFS scratch has an inode quota. Seven lanes at once, three of them
CP2K-sized, put a campaign over a three-million-inode quota, and a check
that only reads the free count at start time admits one lane too many.
The planner decides the cap instead, and the controller reserves what
each lane will hold.

First the footprint table. A ledger record whose ~build~ object carries
~inodes_peak~ says what one build reached; a static table covers
packages the ledger has not seen; the built-in classes cover the rest
(CP2K 350000; LAMMPS, PyTorch, SeisSol, NVHPC, intel 150000; else
60000):

#+begin_src bash
eb-stack stack footprints \
  --ledger ledger/2025.jsonl \
  --table site-footprints.tsv \
  --out footprints.json
#+end_src

Then the plan, with the quota the scratch has and the margin to keep
free:

#+begin_src bash
eb-stack stack shard \
  --build-list genoa.list \
  --easyconfigs easyconfigs \
  --shards 7 \
  --inode-quota 3000000 --inode-margin 100000 \
  --inode-footprints footprints.json \
  --out-dir shards
#+end_src

Each shard in ~shards/plan.json~ now carries ~inode_footprint~, its
largest module footprint plus 1000 inodes per line, and the plan carries
~max_concurrent_shards~, the most shards, largest first, that fit under
2900000 at once. The shard lists are the ones the command writes without
the flags.

Before the controller starts a lane it asks the quota and the scheduler,
and lets ~stack admit~ decide:

#+begin_src bash
eb-stack stack admit \
  --quota-json quota.json \
  --footprint "$(jq '.shards[] | select(.name=="shard-01") | .inode_footprint' shards/plan.json)" \
  --job "$SLURM_JOB_ID" \
  --reservations reservations \
  --live-jobs "$(squeue -h -o %i -u jenkins | paste -sd,)"
#+end_src

~quota.json~ is ~{"inodes_used": U, "inodes_soft": S, "inodes_hard": H}~
from the site's quota command. The lane starts when the available inodes
minus the reservations of the live jobs cover its footprint plus the
margin; the command then writes ~reservations/<job>.json~ and exits 0.
Otherwise it exits 78 and the controller waits. A reservation of a job
no longer in the live list is dropped on the way. ~eb_stack_footprints~
and ~eb_stack_admit~ are the same commands over MCP.
